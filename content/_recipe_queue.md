**変えるときはこの節だけ直す。**

## 🔁 題材の優先順位（2026-08-13 オーナー指示）

**自動化・ループもの（定期実行・監視・置くだけで走る形・毎回自動で繰り返す形）を、
ワンショットの頼み方レシピより優先する。**上から順に書く仕組みなので、
**並び順そのものが優先順位**＝補充・整理のときは自動化ものを上に置く。
ワンショットの題材を書くときも、**「毎回やるなら自動にする」への昇格導線を本文に入れる**
（既存の型＝「毎週やっているなら、決まった時刻に動かす」）。
理由＝読者は「自動化したい非エンジニア」で、このサイトの差別化は「実際に回している」こと。

## 🔥 「定説を実測する」型（2026-08-14 オーナー指示）

**世に出回っている「AIにはこう頼むとよい」を、実際に試して一歩進める型。**
ネタ探し担当が源②（書籍・新刊）から拾ってくるので、キューにこの形の題材が入ってくる。

🔑 **なぜ二番煎じにならないか＝本は測らないから。**本は「こう頼むとよい」で止まる。
**そう頼んだら実際にどう返ったか**は紙には書けない（書いた時点のモデルの話になる）。
このサイトは架空データで試して機械で判定できる。**同じ論点から始めても中身が違う。**

| | |
|---|---|
| 入口 | 「よく言われる〜」「一般に勧められる〜」＝**主張は一般化して扱う** |
| 中身 | 実際に試して、**どこまで本当か・どこで崩れるか**を機械で判定して出す |
| 出口 | 崩れたところの**言い直し方**（受け皿つきで渡す＝台帳★1） |

📌 **「定説は正しかった」で終わってもよい。**確かめた事実自体に値打ちがある。
⚠️ ただし**確かめずに「正しい」と書かない**——それは本の要約になる。
🚨 **本文を写さない**（著作権）。🚨 **書名を出して「この本は間違い」と書かない**
（主張は一般化する。名指しの否定を避けるのは詐欺の節と同じ線）。書評は書かない。

## 💰 稼ぎ方の記事を書くとき（2026-08-15 稼ぎ方研究の設計）

**金額は `money-note` ブロックの中だけに書く。**素の文で「月◯万円稼げる」と書かない。

<div class="money-note">
金額の目安: 月1〜6万円（副業帯）
根拠: 文字単価0.5〜3円（出典: &lt;a href="https://…"&gt;○○公表価格&lt;/a&gt;・2026-08-15確認）× 月2万字の場合
この金額は目安であり、収益を保証するものではありません。
</div>

3点（**出典リンク・確認日・免責の一文**）が揃っていないと
**`validate.py` がビルドを止める**。出典と計算式は研究パック
（`content/_earn_research.md` から `### 副業` 節に入る）に書いてあるので、
**そのまま写す**（自分で調べ直さない・AIに相場を聞かない）。

🚨 **書き方の罠が2つある**（2026-08-15 に実測で確認）:

1. **ブロックの中では Markdown のリンク記法が効かない。**`[出典](https://…)` と
   書いてもリンクにならず、検査が「出典のリンクがありません」で止まる。
   **生のHTMLで `<a href="https://…">○○</a>` と書く**（生HTMLブロックの中は
   Markdown の処理が走らないため）
2. **4スペース以上インデントしない。行頭から書く。**Markdown がコードブロックと
   解釈して、**読者に生HTMLがそのまま見える**（divですらなくなる）。
   ⚠️ 2026-08-15 まで、この形は**検査も素通りしていた**（ブロックが見つからないので
   「金額を書いていない記事」と同じ扱いになっていた）。いまは化けた形を見つけて止める

🚨 **手数料を引く前か後かを必ず書く。**公表されている「相場」は、たいてい
**クライアントが払う額**であって、働いた人の受取額ではない。
（例＝クラウドワークスは10万円以下の部分に**システム利用料20%**＋振込手数料。
文字単価1円×月2万字は契約額2万円でも、**受取は約16,000円**）。
**手取りで書く**か、**「手数料を引く前の額」と明記する**か、どちらかにする。
⚠️ 黙って発注相場を使うと、うちが `too-good-offer-checklist` で読者に警告している
「盛られた数字」を自分がやることになる。

**3帯の縛り**＝副業帯（月数万円）は標準どおり／準本業帯（月数十万円）は
**作業量の前提を明示**（週何時間相当か）／事業帯（月百万円超〜）は
**構造の解説として書く**＋**「到達するのはごく一部」を必ず明記**（生存者バイアス）。

🚨 **収益を保証する断定は書かない**（「必ず稼げ」「確実に稼げ」等は検査で止まる）。
🚨 **投資・トレードで稼ぐ系は書かない**（黒レーン）。

## 担当が守ること（ここが品質の本体）

0. 🚨 **本数は目標であって、ノルマではない。**3本ぶんの題材を、下の1〜6を全部
   守って書けるときだけ3本出す。**守れないなら2本でも1本でもよい。**
   ⚠️ **本数を増やすとき、最初に削られるのが1番（実際に試す）。**そこが消えると
   このシリーズは「それらしい指示文の一覧」になり、価値がまるごと無くなる。
   **3本埋めるために試さずに書くくらいなら、1本にして残りを `- [!]` で止めること。**
   ⚠️ **最後の報告に「何本公開したか」を必ず書く。**目標より少ないときは、その理由と、
   書かなかった題材を `- [!]` にしたことも書く。**足りないことが報告されないと、
   人が数えるまで誰も気づかない**（2026-08-10 に実際に起きた）。

1. **公開する指示文は、必ず自分で実際に試す。**試して返ってきたものを見てから書く。
   試していない指示文を「こう返ってきます」と書かない。**3本とも個別に試す**
   （1本目で試したから他も大丈夫、は成り立たない）
2. **既存記事と重複させない。**書き始める前に全記事の見出しを並べて衝突を確かめる
   （集約型で実際に丸かぶりを踏んだ。SESSION_HANDOFF の「次に書く記事」節参照）。
   ⚠️ **同じ晩に書く3本どうしの重複も見ること。**公開済みとだけ突き合わせると、
   3本が似た切り口になっても検知できない。**1本書くたびに、次の題材が
   それと衝突しないかを確かめ直す**（並行ではなく1本ずつ順に書く）
3. **体験の語り口で書かない。**「私はこれで成功した」ではなく「こう頼むとこう返る」。
   これが崩れると全自動で公開してよい根拠が消える
4. **図を1枚以上。**`tools/make_figures.py` に関数を足して座標は計算で出す（手描きしない）
5. **既存記事へ内部リンクを2本以上。**提案型は入口で、本体は既存の実践記事
6. **迷ったら書かずに止まる。**キューに `- [!]` と理由を書いて終わる。
   薄い記事を1本出すより、何も出さないほうが良い
7. **図は3本ぶん別々に作る。**`make_figures.py` に3つ関数を足す。
   ⚠️ **同じ図を使い回さない**（アイキャッチは scene で自動的に変わるが、本文の図は別）
8. **最後に `python -m tools.make_eyecatch` を1回。**書いた本数ぶんのアイキャッチが要る。
   ⚠️ **先に `git pull`**（他の担当が push していると、その記事だけ取り残される）
9. **書く前に `content/_lessons.md`（書き方の台帳）を全部読んで適用する。**
   過去の担当が実際に試して踏んだ失敗の蓄積で、ここを読まないと同じ穴に落ちる。
   新しく学んだことがあれば「生きている教訓」に足す（**ノルマではない**。**追記のみ**で、
   既存の教訓と「昇格済み」欄は書き換えない）。
   ⚠️ **既にある教訓の再発なら「N番が再発した」と書く**（番号を増やさない）。
   同じ教訓が2回出たら昇格の条件を満たすので、週次の昇格判定で拾えるようにしておく
10. **試した記録を `docs/evidence/<slug>.md` に残す**（様式＝`docs/evidence/TEMPLATE.md`）。
   記事に載せる指示文すべてについて「入力・送った指示文（記事と同一文字列）・
   返ってきたもの（生）・判定」。⚠️ **返ってきたものを要約しない**（要約は、書いてある
   ことを消す）。⚠️ **`content/` の中に置かない**（ビルド除外は**ファイル名**の `_` 判定
   なので、`content/` 配下だと記事として拾われる）
11b. **未処理が3件を切ったら、自分で題materを足してよい**（枯れて止まるより良い）。
   材料＝`docs/topic-candidates/` の**いちばん新しいファイル**（毎週土曜に自動で更新される。
   `python -m tools.suggest_topics automate` で今すぐ回すこともできる）。
   ⚠️ **語数の多い順に採らないこと。**採否の理由は語数からは出てこない——
   2026-08-14 の実測では**実質語数の上位3つが1件も採用にならなかった**
   （note 186＝収益化でお金直球／コンサル 133＝業界と就職の話で読者像違い／
   kindle 108＝出版でグレー）。**各節の縛りと既存記事との切り分けを書けないものは採らない。**
   足したら、根拠（語数と実際の言い回し）と見送った理由もキューに残すこと。

11. 🚨 **push 先は必ず origin の main。**作業ブランチ（`claude/...`）にいる場合は
   main へマージするところまでやり、**`git log origin/main -1` で自分のコミットが
   載ったことを目で確かめる**。⚠️ **main に入っていないとサイトは更新されない**
   （2026-08-11 に実際に起きた＝2本書いて push まで済ませたのに、作業ブランチに
   入ったままサイトには1本も出なかった）

⚠️ 密度の下限（指示文6個・図1枚・内部リンク1本・本文1800字）は `validate.py` が
ビルドで強制する。**下限を満たすことは目的ではない。**満たしていても中身が薄ければ止める。
