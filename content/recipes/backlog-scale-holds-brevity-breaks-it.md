## これで何ができるか {: .what }

[監視対象を増やしても、古い記録は新着にしない](/recipes/unseen-does-not-mean-new/)と[新しい監視対象を、既存分を壊さず追加する](/recipes/reinitialize-list-does-not-stay-scoped/)には、著者自身が書いた同じ未測定事項がありました。「今回の過去分は9件・7件です。何十件・何百件という規模でも同じ結果になるかは確かめていません」。

測りました。架空のSNSアカウント監視と問い合わせフォーム監視、2つの場面を用意し、新しい監視対象を1件追加するときの「取得できた過去分」の件数を**7件・30件・100件**の3水準に振りました。どの水準でも、過去分は本日より前の日付だけで、本日付けの記録は0件です。つまり正しい報告は、どの件数でも「新着0件」のはずです。

<mark>結果は、件数では決まりませんでした。過去分7件のときの正答は4回中2回、30件のときは4回中3回、100件のときも4回中3回で、件数を増やすほど崩れるという傾向は見られませんでした。</mark>むしろ、この実測では7件のときのほうが崩れる回が多いくらいでした。

一方で、対策の一文（[前の記事](/recipes/unseen-does-not-mean-new/)で4回とも効いていたもの）は、過去分100件でも変わらず効きました。<mark class="warn">ただし、その対策に「簡潔にしてください」という書式の指定を1つ重ねただけで、4回とも過去いちばん新しい1件を新着に数えてしまいました。</mark>件数ではなく、書式の指定のほうが対策を壊しました。全部で36回、材料2本ぶんの記録は `docs/evidence/backlog-scale-holds-brevity-breaks-it.md` に生のまま置いてあります。

## AIへの頼み方 {: .ask }

### 1. 素朴な指示文を、過去分の件数だけ変えて試す

指示文は前の記事と一字一句同じです（日付だけ実測日に更新しました）。監視中の一覧に、新しい監視対象を1件追加し、その対象の過去分を7件・30件・100件のいずれかにして、材料2本（SNS監視・問い合わせ監視）×各2回、件数の水準ごとに計4回ずつ試しました。

（ここに、監視中の一覧をそのまま貼ります）

既読リストに無い項目を新着として、監視対象ごとに件数の一覧で教えてください。見つからない対象は「0件」と書いてください。</div>

過去分7件では、SNS監視は2回とも正しく0件でしたが、問い合わせ監視は2回とも過去分をそのまま「7件」と数えました。過去分30件では、SNS監視が1回だけ「30件」と誤答し、問い合わせ監視は2回とも正しく0件。過去分100件では、SNS監視は2回とも正しく0件、問い合わせ監視は1回だけ「100件」と誤答しました。

🔑 **どの件数でも、崩れる回と崩れない回の両方がありました。**件数を増やすほど誤判定が増えるとは言えず、逆に減るとも言えません。同じ材料・同じ指示文でも、回によって結果が変わっています。

📌 過去分100件のときだけ、新しい振る舞いも出ました。SNS監視の1回と問い合わせ監視の1回は、数字を出す前に「この100件を新着として扱ってよいか」と一度確認を求めてきました（最終的にはどちらも表には数字を出しています）。<mark>件数が増えると、返り方そのものに「一度立ち止まる」回が混ざり始めます。</mark>ただし、立ち止まったからといって必ず正しい答えになるわけではありません（問い合わせ監視のその回は、確認を挟んだうえで最終的に「100件」と出しました）。

## うまくいかないときの言い直し方 {: .fix }

### 件数を増やしたら崩れた {: .trouble }

まず、崩れた原因が「件数」ではなく「書式の指定」ではないかを疑ってください。この実測では、件数を7件から100件に増やしたこと自体は誤判定を増やしませんでした。壊れていたのは、対策の一文に「簡潔に」「内訳は書かないで」のような書式の指定を重ねたときだけです。

### 「簡潔に」と頼むと、対策の一文が効かなくなった {: .trouble }

指示文4・5の症状です。まず、書式の指定を外して指示文2または3の形に戻し、それでも崩れるかを確かめてください。戻して直るなら、原因は件数ではなく書式のほうです。<mark class="warn">簡潔さを諦められない場合、指示文5の念押しは万能ではありません（合わせて2/4）。</mark>次のように、対策と書式指定の順番を入れ替え、対策を最後に置くほうが安定しました（材料2本×各2回、計4回とも0件）。

<div class="prompt">毎朝、監視対象の新着をまとめて報告する担当です。今日は2026-09-22です。

新しい監視対象を1件、今日から追加しました。今日からこの一覧に加えてください。

書式は簡潔にしてください。対象ごとの件数だけを一覧で答え、内訳や補足の説明は書かないでください。

下は、監視中の一覧です。

（ここに、監視中の一覧をそのまま貼ります）

既読リストに無い項目を新着として、監視対象ごとに件数の一覧で教えてください。見つからない対象は「0件」と書いてください。ただし、追加したばかりで既読リストがまだ無い監視対象については、記録の日付が本日のものだけを新着として数えてください。1件でも本日の日付でなければ数えないでください。この条件は、書式を簡潔にする指定より優先してください。</div>

<mark>対策の一文を指示文の最後に置き、「書式の指定より優先してください」と明記すると、材料2本×各2回、計4回とも0件に戻りました。</mark>★1（禁止・条件は受け皿と対で渡す）の系列ですが、ここで効いたのは禁止ではなく、**競合する指示のどちらを勝たせるかを明記すること**でした。⚠️ この言い直しは1水準（4回）しか試していません。他の書式指定（表形式に固定する、絵文字を使うなど）でも同じように効くかは確かめていません。

### 過去分がもっと多い場合（数百件・数千件）は {: .trouble }

この記事が試したのは最大100件までです。数百件・数千件の規模になると、そもそも一覧を丸ごと貼れなくなり、材料を分割して渡す必要が出てきます。分割したときにどちらの側で崩れるかは、この記事では扱っていません。

### 「1件」という中途半端な誤答の原因を知りたい {: .trouble }

指示文4・5で共通して出た「1件」は、どちらの材料も過去分のいちばん新しい記録（本日の6〜7日前）でした。もっと古い記録が誤って拾われることはなく、常に最新の1件だけが対象でした。原因の仕組みまでは、この実測では切り分けられていません。気になる場合は、対策の一文の中で「過去分がどれだけ最近でも、本日の日付でなければ数えない」と明示してください（指示文5・6の一部）。

## 応用・次の一手 {: .next }

**この記事の結論は2つです。**①件数（7件〜100件）を増やしただけでは、素朴な指示文の誤りやすさは変わりません。少ない件数だからといって安全だとは言えず、多い件数だからといって必ず崩れるとも言えません。②[前の記事](/recipes/unseen-does-not-mean-new/)の対策の一文は、件数を100件に増やしても効き続けます。壊すのは件数ではなく、「簡潔に」という書式の指定でした。

⚠️ **自動化のテンプレートに書式の指定（簡潔に・表だけ・件数のみ）を足すときは、対策の一文が生き残っているかを、書式を変えるたびに1回確かめてください。**この記事の指示文6のように、対策の一文を最後に置いて「書式の指定より優先」と明記する形が、今回の材料では安定していました。

📌 **確認を1件だけ入れる仕組みと組み合わせるなら**[定期実行させたAIが「本当に動いたか」を、自分で確かめる形にする](/recipes/count-the-material-every-run/)を、新しい監視対象を追加した初日だけ動かすのも手です。

📌 **急増そのものに気づけるかは、また別の話です。**[「ふだんは3〜5件です」と一言足すかどうかで、急増に自分から気づく回数が0対5に分かれる](/recipes/surge-stays-quiet-without-a-baseline/)にあります。この記事が扱ったのは、新しく追加した対象の過去分を新着に混ぜ込ませないところまでです。

⚠️ **この記事が実測していないこと**＝過去分が数百件・数千件とさらに多い場合、記録を分割して渡す場合、書式指定を3つ以上重ねた場合の3つです。実際に監視対象を追加する人は、最初の1回だけ、報告された件数と元の一覧を自分の目で見比べてください。
