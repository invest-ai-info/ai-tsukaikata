## これで何ができるか

**AIに毎回同じ説明をしなくて済むようになります。**

AIとの会話は、ウィンドウを閉じた瞬間に全部忘れられます。翌日には「このプロジェクトは何で」「私はこういう方針で」を最初から説明し直しです。相談相手としては、これは致命的に不便です。

やることは単純で、**覚えておいてほしいことをファイルに書いておくだけ**です。それだけで、

- 「いつもの書き方で」が通じる
- 3ヶ月前に決めた方針を蒸し返されない
- 一度指摘したことを二度言わなくて済む

この記事では、実際に35個の記憶ファイルを運用して分かった**「何を書くと役に立ち、何を書くと害になるか」**を書きます。仕組みを作るのは20分ですが、**書く内容を間違えると逆効果になります。**そこが本題です。

置き場所は3つに分けます。

|---|---|
| かかる時間 | 20分 |
| 費用 | 無料 |

## 手順

### 1. まず `CLAUDE.md` を置く

一番簡単で、一番効果が大きいのがこれです。プロジェクトのフォルダに `CLAUDE.md` という名前のファイルを置くと、**会話のたびに自動で読み込まれます。**

Claude Code なら `/init` と打つと、リポジトリを読んで下書きを作ってくれます。それを叩き台に手で直すのが早いです。

書くのはこういうことです。

```markdown
# このプロジェクトについて

毎朝7時に自動でデータを更新して公開するサイト。

## 開発のルール
- テストは `python -m pytest -q` で全部通してから commit する
- 日本語のコメントを書く。英語にしない
- 依存を増やすときは必ず相談する

## 触ると壊れるところ
- `config/sources.yml` は本番が読んでいる。書式を変えない
- `data/` 配下は自動生成物。手で編集しない
```

**「触ると壊れるところ」を書くのが一番効きます。**AIは善意で親切に、壊してはいけないものを整理してくれます。先に線を引いておくと事故が減ります。

自分専用の設定（どのプロジェクトでも共通の好み）は、ホームフォルダの `.claude/CLAUDE.md` に置けます。

### 2. 1ファイル1事実で「記憶」を作る

`CLAUDE.md` は毎回全文が読み込まれるので、**何でも書くと膨れ上がります。**プロジェクトの前提を超えて「自分のこと」「過去の判断」まで貯めるなら、別ファイルに分けます。

使っている構成はこうです。

```
memory/
├─ MEMORY.md                    ← 索引。1メモリ1行だけ
├─ project_xxx.md               ← 進行中の案件
├─ feedback_yyy.md              ← 「こう働いてほしい」という指示
├─ user_profile.md              ← 自分がどういう人間か
└─ reference_zzz.md             ← 外部リンク・ダッシュボード
```

1ファイルはこういう形にします。

<figure class="figure">
<img src="/static/images/memory-file-anatomy.svg" alt="記憶ファイル1枚の構造。上に名前・一行説明・種別を書き、その下に何が起きたかを絶対日付で書く。さらにWhyとしてなぜそうするのかを書き、How to applyとして次にどうするかを書く。WhyとHow to applyが無いと、半年後に読んだときにまだ有効なルールか判断できない。">
<figcaption>一行説明は「この記憶が今の話に関係あるか」の判定に使われるので、内容が分かる形で書きます。</figcaption>
</figure>

```markdown
---
name: feedback_date_freshness
description: 日付を書き込む直前に必ず現在時刻を取り直す
metadata:
  type: feedback
---

セッションが中断され、3日後に再開された際、会話の冒頭で取得した日付を
そのまま使って記事を誤った日付で公開する事故が起きた。

**Why:** 会話は日をまたいで中断・再開されることがあり、冒頭で取った
時刻は再開時点では古い。

**How to apply:** 日付を書き込む直前に必ず時刻を取り直す。冒頭の値を
使い回さない。関連: [[project_publish_flow]]
```

**`Why` と `How to apply` を必ず書いてください。**これが無いと、半年後に読んだときに「まだ有効なルールなのか」が判断できません。事実だけのメモは、古くなったとき捨てていいのか残すべきなのか分からず、結局全部信用できなくなります。

`[[ほかのメモの名前]]` で相互にリンクしておくと、関連するものを芋づるで引けます。まだ存在しない名前を書いても構いません。**「これは後で書くべきだ」という印**になります。

### 3. 索引ファイルを作る

`MEMORY.md` は**1メモリ1行だけ**にします。

```markdown
- [自分のプロフィール](user_profile.md) — 兼業・非エンジニア・自動化重視
- [進行中: サイト構築](project_site.md) — 8月公開目標。記事5本から
- [指示: 法務リスクの書き方](feedback_legal_risk.md) — 白/グレー/黒で分けて示す
- [参考: 価格データの取り方](reference_price_api.md) — 公式APIを直接叩く
```

**ここに中身を書いてはいけません。**索引は毎回読み込まれるので、中身を書くと結局全部読み込むのと同じになり、分けた意味が消えます。

### 4. セッションをまたぐ引き継ぎメモを置く

記憶とは別に、**「次に何をするか」**専用のファイルを1つ作っておくと効きます。

```markdown
# SESSION_HANDOFF

最終更新: 2026-08-01 22:12 JST

## 現在地
3段構えの1段目が完了・本番稼働中。次は2段目。

## 次のセッションでやること
1. 設計書 `docs/specs/xxx.md` を読む
2. 実装計画を作る
3. 実装する

## 設計上、触ると壊れるところ
- 初回は必ず `--mode bootstrap` を先に実行する。
  これをせずに通常運転すると1000通超のメールが飛ぶ
```

翌日の会話の最初に「このファイルを読んで続きをやって」と言うだけで再開できます。**記憶は「変わらないこと」、引き継ぎメモは「今どこにいるか」**と分けると、どちらも腐りにくくなります。

## つまずいた点と直し方

### リポジトリを読めば分かることは書かない

一番やりがちな失敗です。「このプロジェクトのフォルダ構成は」「あの関数はこういう作りで」と書きたくなりますが、**書いてはいけません。**

コードは変わります。記憶は変わりません。**数ヶ月後、記憶のほうが嘘になります。**しかもAIはその嘘を信じて動くので、何も書いていないより悪い状態になります。

書くべきなのは、**コードを読んでも絶対に分からないこと**です。

<figure class="figure">
<img src="/static/images/memory-what-to-write.svg" alt="記憶に書くことと書かないことの対比。書くのは、なぜその方式を選んだか、何を試して駄目だったか、自分がどう働いてほしいか、外部の事情や制約。書かないのは、どういう作りになっているか、何が実装されているか、過去の修正履歴、ファイル一覧。前者は変わらないが、後者はすぐ変わって記憶のほうが嘘になる。">
<figcaption>「なぜ」は変わりません。「何」はすぐ変わります。迷ったときの目安は「同じ指摘を2回したか」です。</figcaption>
</figure>

「なぜ」は変わりません。「何」はすぐ変わります。

### 相対日付を書かない

「先週」「来月まで」「最近」と書くと、**読み返した時点で意味がずれます。**AIにとって「先週」は今日から見た先週です。

必ず絶対日付で書いてください。

- ❌ 「先週から自動投稿を止めている」
- ⭕ 「2026年7月20日から自動投稿を止めている」

これは実際に事故になりました。会話が数日中断して再開したとき、**冒頭で取った日付をそのまま使って**、間違った日付で公開してしまったことがあります。日付は「使う直前に取り直す」を徹底してください。

### 1ファイルに詰め込まない

1つのファイルに10個の事実を書くと、そのうち1つが古くなった時点で**ファイル全体が信用できなくなります。**「どこが古いか」を確認する手間が、読む価値を上回ります。

1ファイル1事実にしておけば、古くなったものだけを消せます。

### 間違った記憶は消す

追加するばかりで消さないと、矛盾した記憶が同居します。AIはどちらを信じればいいか分からず、状況によって挙動が変わります。

**方針が変わったら、古いほうを消してください。**上書きするのが理想です。「以前はAだったが今はB」という書き方は、Aのほうを拾われる余地を残すので避けます。

### 記憶は「書いた時点のスナップショット」だと扱う

これは受け取る側（AI）にも守らせるべきルールです。

記憶に「`config.yml` の `retry` を3にしてある」と書いてあったとして、**それは書いた時点の話**です。今もそうとは限りません。ファイル名・関数名・設定値が出てくる記憶は、**使う前に実物を確認する**のが正しい扱い方です。

だから記憶には、なるべく**具体的な値ではなく判断基準**を書きます。「retryは3」ではなく「一時的な失敗で鳴らないよう、複数回連続で失敗してから警告する方針」と書けば、値が変わっても嘘になりません。

### 会話の中だけで意味があることは書かない

「さっきの件で」「この修正について」のような、その会話でしか通じないものを記憶に入れると、後で読んで何の話か分かりません。

書く前に自問してください。**「これは3ヶ月後の自分が読んで意味が分かるか」**。分からないなら、分かる形に書き直してから保存します。

### 何を書くか迷ったら「二度言ったこと」

判断に迷ったときの目安はこれです。**同じ指摘を2回した内容は、記憶に書く価値があります。**

1回目は偶然かもしれませんが、2回言ったなら3回目もあります。3回目を言わずに済ませるのが、この仕組みの目的です。

## 応用・次の一手

**まず `CLAUDE.md` を1枚書いてください。**「触ると壊れるところ」を3行書くだけでも、その日から効果が出ます。

記憶ファイルまで作るのは、同じ説明を繰り返している自覚が出てきてからで十分です。**先に立派な仕組みを作っても、書く中身がなければ空箱です。**

慣れてきたら、記憶に「作業のやり方」そのものを書くと効きます。「公開前にはこの3つを確認する」「この判断は必ず人間に確認を取る」といったものです。ただし、**本当に守らせたいルールは、記憶ではなくコードで強制してください。**記憶は「お願い」ですが、コードは「保証」です。

この考え方を実際に形にしたのが [サービスが静かに壊れたのを自動で見つける](/recipes/auto-health-check/) と、[AIの最新情報を自動で集める](/recipes/ai-news-auto-collect/) の初期化ガードです。どちらも「気をつける」ではなく「気をつけなくても壊れない」形にしてあります。
