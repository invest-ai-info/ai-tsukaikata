## これで何ができるか {: .what }

[工程を分けて頼むと崩れるか](/recipes/split-into-stages-what-breaks/)は、架空の問い合わせ処理を3工程に分けても精度は上がらないことを確かめました。ただし、各工程の冒頭に「受け取った件数」を書かせれば崩れを止められることも分かっています。<mark>今回はそのチェーンに工程4（担当部署への振り分け）・工程5（部署別の集計表）を足し、5工程まで増やしても崩れないかを試しました。</mark>

前の記事が実際に返した工程3の出力（4本・1字も変えていない）を、そのまま工程4への入力にしています。結果は次の4つです。

1. **工程4（部署振り分け）は、4通し・48件すべてが真値どおりでした。**欠落0・誤りも0です。
2. **工程5（集計表）も、4通しとも4セル（営業部・サポート部・総務部・合計）が真値どおりでした。**
3. <mark>工程3で「期限」欄が本工程に届かず機能しなくなっていた3本（A-1・B-1・B-2）でも、工程4・5は崩れませんでした。</mark>部署の判定も集計も、期限を使わないからです。
4. <mark class="warn">工程3を完全に0件で止めた場合を試すと、工程4は作り話で埋めず「受け取った件数: 0件」と理由を引き継いで止まりました。</mark>停止は後工程にも正しく伝わり、下流が勝手に12件を復元しようとはしませんでした。

📌 **この記事の数字はすべて架空データでの実測です。**実在の個人・企業の情報は含みません。工程4・工程5とも**独立した新規会話**（この実測の目的も、前後の会話も知らない）で走らせました。材料2本×各2回＝4通しに、工程3が完全に止まった場合を見る追加の1回を加えています。生の返りと機械照合は `docs/evidence/later-stages-skip-the-gap-and-stay-clean.md` に全文置いてあります。

## うまくいかないときの言い直し方 {: .fix }

### 工程を増やしたら、どこかで崩れるはずだと思っていた {: .trouble }

今回の実測では崩れませんでした。<mark class="warn">ただしこれは「工程を増やしても安全」という意味ではありません。</mark>崩れなかった理由は、新しく足した工程4・5が、前段で欠けていた項目（期限）を**必要としなかった**からです。部署を決めるのも、件数を数えるのも、期限を見ません。

📌 **足す工程を選ぶときは、その工程が前段のどの項目を使うかを先に書き出してください。**使う項目が前段で欠けていた項目と重なるなら、この記事の結果は当てになりません。⚠️ **この組み合わせ（欠けた項目を使う工程を足した場合）は、今回は試していません。**次に測るならここです。

### 工程3が完全に止まったら、そこで終わりだと思っていた {: .trouble }

工程3が0件で止まった場合（前の記事の別の版）を、同じ工程4の指示文に渡してみました。

<div class="prompt">はじめに、受け取った件数を「受け取った件数: ◯件」の形で書いてください。前の工程から件数が増えたり減ったりしている場合は、その理由も書いてください。
下は、3行にまとめた問い合わせの一覧です。1件ずつ内容を読んで、担当部署に振り分けてください。見積もりに関する依頼は営業部、故障や不具合の相談はサポート部、日程の調整や確認は総務部です。元の3行はそのまま残し、4行目に「担当部署: ◯◯部」を追加してください。</div>

渡したのは、工程3が「3行のまとめは作れませんでした」と断った文面です（12件分の型番・用件・期限は1件も含まれていません）。

> 受け取った件数: 0件
>
> （…）今回は「1件ずつ内容を読んで担当部署に振り分ける」という作業を実行できません。振り分けの判断材料になる問い合わせ本文がありません。M-05〜M-09の注記だけでは、実際の問い合わせ内容か分類メモかが分かりません。ここだけで「サポート部」と決めると、誤った振り分けになるおそれがあります。

<mark>作り話で部署を割った件数は0です。</mark>「受け取った件数: 0件」と正しく自己申告し、前工程が挙げていた「本文の要旨と期限をもらえれば作る」という条件まで、そのまま次の工程にも引き継いでいます。**停止は、工程を1つ足しても消えずに伝わりました。**

## 応用・次の一手 {: .next }

**工程を増やすこと自体は、今回の実測では精度を下げませんでした。**ただし、それは新しく足した工程が前段の欠けを使わなかったという条件のもとでの話です。自動化のチェーンに工程を足すときは、**その工程が前段のどの項目に依存するかを先に確認してください。**依存する項目が前段で欠けやすい項目と同じなら、この記事の結果をそのまま当てにしないでください。

[止まった日のメモだけで再開する](/recipes/memo-that-names-the-next-row/)は、AIの「できませんでした」が次の工程に届かないと、その先が止まったまま気づかれない形を測りました。今回は逆に、**停止がきちんと次の工程にも届く**ことを確かめた形です。[工程2に確認させると誤りは直る](/recipes/doubt-fixes-added-not-dropped/)は、上流の誤りを下流が見つけられるかを測っています。

⚠️ **この記事が実測していないこと**は2つです。

- 足した工程4・5が、前段で欠けていた項目（期限）を実際に必要とする場合にどうなるか。今回は「部署」「集計」という、期限を使わない作業だけを足しました
- 工程を6つ、7つとさらに増やした場合にどうなるか。今回は5工程までしか測っていません

次に測るなら、**欠けた項目をまさに使う工程**を足します。たとえば工程4の代わりに「期限が今週中かどうかで対応の緊急度を判定する」という工程を足し、同じチェーンがどこで崩れるかを見ます。
