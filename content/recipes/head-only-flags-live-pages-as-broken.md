## これで何ができるか {: .what }

自分のブログやポートフォリオに貼ったリンクが切れていないか、点検結果をAIに読ませて「どれが本当に切れているか」を判断させる頼み方です。プログラミングは要りません。

多くの点検スクリプトは、速さのために**HEADリクエスト**（ページの中身を受け取らない軽い確認）だけで済ませます。ところが<mark class="warn">HEADに404を返すのに、GETリクエストには200（正常）を返すサイトが実在します。</mark>このサイト自身が、週次の検査で実際に踏んだ事例です。HEADの結果だけをAIに渡すと、<mark>生きているページ4件を含めて12件を「切れている」と判定しました。</mark>架空のリンク20本・2材料×各2回＝4回とも、です。

<figure class="figure">
<img src="/static/images/head-only-flags-live-pages.svg" alt="架空のブログのリンク一覧20本（本当に切れている8本・HEADは404だがGETは200の4本・HEAD/GETとも403でボット判定の可能性がある4本・正常4本）を、3つの渡し方でAIに判定させた図。HEADの応答コードだけを渡して素朴に聞いた場合は、2材料×各2回の4回とも、本当は生きている4本を含めて12本を切れていると判定した。HEADだけでは確定できないと言い添えて同じHEADのデータを渡した場合は、4回とも、404や403のリンクを切れているとは断定せず確認が必要な扱いに分けた。HEADとGETの両方の応答コードを渡して素朴に聞いた場合は、4回とも生きている4本を誤判定に含めず、ボット判定の可能性がある4本も切れているとは断定しなかった。">
<figcaption>HEADだけだと4回とも誤判定。GETの結果を渡すか、判断を保留させれば、誤判定は0回になる。</figcaption>
</figure>

<mark>GETリクエストの結果もあわせて渡すと、この誤判定は4回中0回に消えます。</mark>ボット対策で403を返しているだけのページも、4回とも「切れている」と決めつけませんでした。人がブラウザで開けば見られることがあるページは、確認が必要な扱いに分けています。

ただし、ここで終わりではありません。**判断の基準を数字で明示すると、別の問題が出ます。**見出しに書いた件数が、実際に列挙した件数と食い違う回が、8回中6回ありました。「言い直し方」の節で、原因と直し方を書きます。

## 前提 {: .need }

| | |
|---|---|
| かかる時間 | 20分 |
| 費用 | 無料 |
| 必要なもの | リンクごとにHEAD（とできればGET）の応答コードが分かる点検結果 |
| プログラミング | **不要**。この記事の指示文をコピーして貼るだけです |

**この記事は「点検結果をAIにどう読ませるか」だけを扱います。**HEADやGETの応答コードをどう取得するかという、点検スクリプト自体の作り方は範囲外です。すでに自動で動いている点検の仕組みを持っている前提で読んでください。「機械の検査をAIに作らせる」頼み方は、[サービスが静かに壊れたのを見つけさせる](/recipes/auto-health-check/)や[AIに作らせた図の崩れを検査で止める](/recipes/catch-broken-figures/)と組み合わせてください。

## AIへの頼み方 {: .ask }

### 1. まず、HEADだけの点検結果を渡してみる

架空のブログに貼った20本のリンクを用意しました。構成は次の4種類です。

- 本当に切れている：8本
- HEADは404だがGETは200：4本（Googleのヘルプページ等で実際に起きる形）
- HEAD/GETともに403で、ボット判定の可能性がある：4本
- 正常：4本

まずHEADの応答コードだけを渡しました。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストの応答コードを記録しています。この中でリンク切れになっているものを教えてください。</div>

（この下に、点検結果の一覧をそのまま貼ります。もう1本の材料でも同じ指示文を試しています）

<mark>2材料×各2回＝4回とも、本当は生きている4件を、本当に切れている8件と一緒に「リンク切れ12件」としてまとめました。</mark>生きている4件は、HEADだけ404・GETは200のものです。404を見た時点で切れていると判断し、ボット判定の可能性がある403の4件だけは「判断を保留すべきもの」と分けています。**404と403で扱いを変える判断力はあるのに、HEADの404そのものを疑う材料が無いので、疑えません。**

**なぜこの結果になるか。**AIは渡された情報だけで判断します。GETの応答コードを渡していないので、「HEADの404がGETでも404になるとは限らない」という事実そのものを知る手段がありません。

### 2. 「HEADだけでは確定できない」と言い添える

GETの点検をまだ組み込んでいなくても、言い回しだけで誤判定を避けられるか試しました。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストの応答コードを記録しています。HEADの応答コードだけでは、本当に切れているかは確定できません。404や403のリンクは、GETリクエストでの再確認が必要なものとして分けてください。GETで再確認済みのものは、まだありません。</div>

<mark>4回とも、404と403のリンクをひとまとめにして「GETでの再確認が必要」という保留の扱いに分け、どの1件も「切れている」と断定しませんでした。</mark>本当に切れている8件も、生きている4件も、同じ保留の箱に入ってしまうので取りこぼしは防げますが、**まだ「どれが本当に切れているか」には答えていません。**GETの結果を自分で取るまでの、安全な待ち方として使えます。

### 3. GETの結果もあわせて渡す

点検スクリプトがGETも取っているなら、両方をそのまま渡します。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストとGETリクエストの応答コードを記録しています。この中でリンク切れになっているものを教えてください。</div>

**指示文は1.とほとんど同じで、渡すデータにGETの列を足しただけです。**それでも結果は一変しました。

- 本当に切れている8件だけを「リンク切れ」として、4回とも正しく挙げました
- HEADだけ404の4件は、理由を添えて外しました。「サーバーがHEADリクエストに対応していないだけで、実際にはページを開けます」
- ボット判定の可能性がある403の4件も、4回とも言い切りませんでした。「アクセス拒否の状態です。ブラウザで確認してください」

**なぜこの言い方で足りるか。**HEADとGETという2つの事実を並べて渡すだけで、AIは「HEADが404でもGETが200なら生きている」という関係を自分で組み立てました。判定の基準を数字で指示していないのに、です。

## うまくいかないときの言い直し方 {: .fix }

### 基準を数字で書くと、見出しの件数がずれる {: .trouble }

**自動化に組み込むなら、判断の基準をこちらで固定したくなります。**「GETも404の場合だけ切れている」と明示しました。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストとGETリクエストの応答コードを記録しています。HEADの応答コードだけでは判断しないでください。HEADが404や403でも、GETが200ならそのリンクは切れていません。GETも404の場合だけ、切れていると判断してください。この基準で、リンク切れになっているものを教えてください。</div>

挙げてきたリンクのID自体は、4回とも本当に切れている8件と完全に一致していました。ところが<mark class="warn">4回とも、見出しに書いた件数が実際に列挙した件数と食い違いました。</mark>1回目は「該当は次の10件です」と書いてから8件だけ並べ、「数えると8件でした。訂正します」と自分で直しています。別の回では「次の7件です」から始めて、同じく8件へ訂正しました。**名前の集合は毎回正しいのに、最初に宣言する数字だけが外れます。**

### 「確認できない」の分類を増やしても、半分は直る {: .trouble }

3つめの受け皿（確認できないリンク）を足して、もう少し丁寧な基準にしました。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストとGETリクエストの応答コードを記録しています。HEADの応答コードだけでは判断しないでください。HEADが404や403でも、GETが200ならそのリンクは切れていません。GETも404の場合は、切れていると判断してください。GETが200でも404でもない場合（403など）は、サーバーがロボットを拒否している可能性があり、人がブラウザで開けば中身を見られることがあります。この場合は切れているとは断定せず、確認できないリンクとして分けてください。この基準で、切れているリンクと確認できないリンクを、それぞれ教えてください。</div>

分類そのものは4回とも正しく、切れている8件・確認できない4件・問題なし8件に割れました。<mark class="warn">それでも4回中2回は、見出しの件数（「9件」「3件」）が実際の列挙と食い違いました。</mark>その2回は、本文の中で「数え直すと8件です」「こちらも数え直すと4件です」と自分で訂正しています。受け皿を増やしたぶん、食い違いは4回中2回まで減りましたが、消えていません。

### 件数は、名前を全部挙げたあとに書かせる {: .trouble }

**直し方は、基準を増やすことではありませんでした。**件数を先に宣言させず、箇条書きの後に回す言い方に変えました。

<div class="prompt">次は、ブログに貼っているリンクを自動点検した結果です。それぞれのリンクについて、HEADリクエストとGETリクエストの応答コードを記録しています。HEADの応答コードだけでは判断しないでください。HEADが404や403でも、GETが200ならそのリンクは切れていません。GETも404の場合は、切れていると判断してください。GETが200でも404でもない場合（403など）は、サーバーがロボットを拒否している可能性があり、人がブラウザで開けば中身を見られることがあります。この場合は切れているとは断定せず、確認できないリンクとして分けてください。

まず、切れているリンクのIDだけを箇条書きで全部挙げてください。件数はまだ書かないでください。箇条書きが終わったら、最後に「以上、何件」と書いてください。確認できないリンクも同じ形で、先にIDを全部挙げてから、最後に件数を書いてください。</div>

<mark>2材料×各2回＝4回とも、「以上、8件」「以上、4件」という見出しの数字が、実際に列挙した件数と完全に一致しました。</mark>食い違いは1件も残りませんでした。

<mark class="warn">自動化に組み込むなら、この言い方を使っても、AIが書いた件数をそのまま次の処理に読み込ませないでください。</mark>件数という1語ではなく、箇条書きの行自体をスクリプト側で数えるほうが確実です。この記事の実測でも、食い違った回はすべて数行後に自分で訂正されていたので、**見出しだけを読む設計にすると、訂正前の間違った数字を拾う危険があります。**

## 応用・次の一手 {: .next }

**この記事の値打ちは2つです。**①HEADだけの点検は、本当に生きているページを切れていると誤判定することがあるが、GETの結果も渡すか、判断を保留させるかで避けられること。②判断基準を数字で書くと、AIの見出しの件数そのものが崩れることがあるが、「名前を先に、件数はあとに」と言い直せば直ること。

**毎週この点検を自動で回すなら、**[毎日決まった時刻にAIを動かす](/recipes/github-actions-daily-cron/)**の形に載せてください。**保存版にするのは、この記事の指示文3（HEADとGETを渡して確認できないリンクを分ける版）です。見つかった結果をメールやIssueに残す仕組みは、[サービスが静かに壊れたのを見つけさせる](/recipes/auto-health-check/)で扱っています。

⚠️ **今回試したのはHEADとGET、404・403・200という組み合わせだけです。**リダイレクト（301・302）やタイムアウト、500番台のエラーを混ぜた場合に同じ結果になるかは確かめていません。実測に使ったのは`claude --safe-mode`という実測環境1つだけで、別のAIサービスでは結果が異なる可能性があります。

📌 この記事の実測は、架空のリンク一覧2本・6種類の頼み方・**全24回**です。判定はすべて機械照合で、生の回答は `docs/evidence/head-only-flags-live-pages-as-broken.md` に全文置いてあります。
