## これで何ができるか

**サーバーを1台も借りずに、毎日決まった時刻に処理を走らせられます。**

- 毎朝7時にデータを取得して更新する
- 毎晩、動画やニュースを要約させる
- 毎週月曜にレポートをメールで送る

必要なのはGitHubアカウントだけです。VPSもレンタルサーバーもクレジットカードも要りません。

この記事では、実際に十数本のワークフローを毎日動かしている環境で分かった**「その通りに書いても動かない」ポイント**まで書きます。cronの書き方だけなら公式ドキュメントで足りますが、そこには「なぜ7時のはずが8時に動くのか」は書いてありません。

## 前提

| | |
|---|---|
| かかる時間 | 30分 |
| 費用 | 無料。公開リポジトリなら実行時間は無制限、非公開でも月2000分まで無料 |
| 必要なもの | GitHubアカウント |
| 前提知識 | ファイルをGitHubに置いたことがあればOK |

## 手順

### 1. ワークフローのファイルを作る

リポジトリに `.github/workflows/daily.yml` を作ります。**このフォルダ名とパスは決まっていて、変えられません。**

```yaml
name: Daily Job

on:
  schedule:
    - cron: "27 22 * * *"   # UTC 22:27 = JST 7:27
  workflow_dispatch:        # 手動実行ボタンを出す（必須）

permissions:
  contents: write

jobs:
  run:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: 依存をインストール
        run: pip install -r requirements.txt

      - name: 処理を実行
        run: python my_script.py
```

これをpushすれば、もう動き始めます。設定画面での有効化は不要です。

### 2. cronの書き方

5つの数字は左から**分・時・日・月・曜日**です。

```
┌───── 分 (0-59)
│ ┌─── 時 (0-23)
│ │ ┌─ 日 (1-31)
│ │ │ ┌ 月 (1-12)
│ │ │ │ ┌ 曜日 (0-6、0が日曜)
│ │ │ │ │
27 22 * * *
```

`*` は「毎回」という意味です。よく使う形はこれくらいです。

| 書き方 | 意味 |
|---|---|
| `27 22 * * *` | 毎日 UTC 22:27（JST 翌7:27） |
| `13 7 * * *` | 毎日 UTC 7:13（JST 16:13） |
| `17 * * * *` | 毎時17分 |
| `27 22 * * 1` | 毎週月曜 UTC 22:27（JST 火曜7:27） |

### 3. 手動で動かして確認する

`Actions` タブ → 左のリストからワークフロー名 → `Run workflow`。

**スケジュールが動くのを待たないでください。**書き間違いがあった場合、翌朝まで気づけません。

## つまずいた点と直し方

### 時刻はUTC。日本時間から9時間引く

**GitHub Actions の cron は必ずUTCです。**タイムゾーンの設定はできません。

日本時間から9時間引いた値を書きます。引くと前日になる場合が多いので、そこで間違えます。

| やりたいこと（JST） | 書く値（UTC） |
|---|---|
| 毎朝 7:27 | `27 22 * * *`（前日22:27） |
| 毎日 16:13 | `13 7 * * *` |
| 毎晩 23:43 | `43 14 * * *` |

**曜日指定と組み合わせるときは特に注意してください。**「毎週月曜の朝7時」は、UTCでは日曜の22時です。`* * 1` と書くと火曜の朝に動きます。

### 毎時0分・毎日0時は避ける

これが一番効きます。

`0 * * * *` や `0 22 * * *` のような**キリのいい時刻は世界中の利用者が殺到します**。GitHub側でキューに積まれ、**30〜90分遅れることも、スキップされることもあります**。

`27`・`13`・`43` のような半端な分にしてください。それだけで安定します。

### スケジュールは遅れる前提で作る

`schedule` は **best-effort** です。SLAはありません。空いていれば数分の遅れ、混んでいれば1時間以上ずれることもあります。

だから、こういう設計にしないでください。

- ❌ 「7:00ちょうどに通知が届く」ことを前提にする
- ❌ ジョブの起動時刻を、そのままデータの時刻として記録する

代わりにこうします。

- ⭕ 「おおよそ7時台に届きます」と説明する
- ⭕ 記録するのは起動時刻ではなく**データを取得した時刻**
- ⭕ 「前回からの差分」で処理する。時刻ではなく状態で判断すれば、遅れても・飛ばされても結果は同じになる

分刻みの正確さが本当に必要なら、GitHub Actions ではなく外部のスケジューラ（cron-job.org など）から `workflow_dispatch` を叩く形にしてください。

### スキップされても困る処理は、時刻を多重化する

「遅れる」ならまだしも「**動かない**」ことがあります。これへの対策は、実運用ではこうしています。

```yaml
on:
  schedule:
    # ─── 朝の更新 ─── 4回試行でスキップ対策
    - cron: '27 22 * * *'   # 7:27 JST 本命
    - cron: '57 22 * * *'   # 7:57 JST バックアップ1（30分後）
    - cron: '27 23 * * *'   # 8:27 JST バックアップ2（1時間後）
    - cron: '57 23 * * *'   # 8:57 JST バックアップ3（1.5時間後）
  workflow_dispatch:
```

**1つの時刻に賭けず、30分おきに4回仕掛けます。**どれか1つでも動けば目的は達成されます。

これが成立する条件は、**2回目以降が無害であること**です。スクリプト側で「前回から変わっていなければ何もしない」と判定するようにしておけば、4回動いても更新は1回だけです。

この「何回実行しても結果が同じ」という性質を冪等（べきとう）性と言います。**定時実行を作るときは、時刻を守らせようとするより、何回走っても大丈夫にするほうが圧倒的に楽です。**

### `workflow_dispatch` を必ず入れる

`schedule` だけだと**手動実行ボタンが出ません**。

これが無いと、動作確認も、失敗したときの復旧も、全部「次のスケジュールを待つ」になります。1行足すだけなので必ず入れてください。

```yaml
on:
  schedule:
    - cron: '27 22 * * *'
  workflow_dispatch:   # ← これ
```

### リポジトリに書き込むなら `permissions` が要る

処理結果をリポジトリにコミットして戻す場合、権限が必要です。

```yaml
permissions:
  contents: write
```

さらにリポジトリの `Settings → Actions → General → Workflow permissions` も **Read and write permissions** にします。**両方**必要です。

足りないとこう落ちます。

```
remote: Permission to <user>/<repo>.git denied to github-actions[bot].
fatal: unable to access ...: The requested URL returned error: 403
```

`403` を見たら、まずここを疑ってください。

### 60日放置するとスケジュールが止まる

**リポジトリに60日間コミットが1つも無いと、スケジュール実行が自動で無効化されます。**

自動化が結果をコミットし続けるタイプなら問題になりませんが、「メールを送るだけ」のように何も書き込まない自動化だと、静かに止まります。

止まるとGitHubからメールが来ますが、見落とすと数ヶ月気づきません。心当たりがあれば `Actions` タブで最終実行日を見てください。

### secretsは `env:` にまとめる

各ステップに `${{ secrets.X }}` を書き散らすと読みにくくなります。ジョブ単位の `env:` にまとめてください。

```yaml
jobs:
  run:
    runs-on: ubuntu-latest
    env:
      API_KEY: ${{ secrets.API_KEY }}
      GMAIL_USER: ${{ secrets.GMAIL_USER }}
    steps:
      - run: python my_script.py    # 環境変数として読める
```

複数のステップで使い回せますし、`run:` の中で `$API_KEY` として参照できます。

### ローカルとActionsの二重実行

Windowsのタスクスケジューラなどでローカルでも同じ処理を動かしていると、**両方が同じファイルを更新して履歴が混乱します**。「覚えのない更新」「上書き合戦」の正体はたいていこれです。

判定して片方を止めることもできますが、**どちらか一方に一本化するのが正解**です。両方走らせる必然性は普通ありません。

### ワークフローのファイルだけ更新できない（404の罠）

これは少し上級者向けですが、ハマると原因が分かりません。

Personal Access Token を使ってAPI経由でファイルを更新するとき、**`.github/workflows/` 配下のファイルだけ `404 Not Found` が返る**ことがあります。

これは権限不足です。ただし `403 Forbidden` ではなく `404` で返ってくるので、「ファイルが無い」と誤診しやすいのがタチの悪いところです。

トークンに `workflow` スコープ（Fine-grained なら Workflows permission を Read and write）を追加してください。追加できない事情があるなら、GitHubのWeb画面のエディタで直接編集すれば通ります。

## 応用・次の一手

**まず1つ作って、しばらく放置してみてください。**動き続けることが分かると、任せられる仕事の見え方が変わります。

そのうえで、自動化には必ず**死活監視**を付けてください。自動化で一番怖いのは、エラーで止まることではなく、**エラーを出さずに古い結果を出し続けること**です。詳しくは [サービスが静かに壊れたのを自動で見つける](/recipes/auto-health-check/) に書きました。
