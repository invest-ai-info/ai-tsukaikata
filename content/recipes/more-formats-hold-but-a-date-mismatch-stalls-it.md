## これで何ができるか {: .what }

[書式を変えても対策は確かめ直す](/recipes/format-break-did-not-return/)という前の記事には、著者自身が残した未測定事項が3つありました。そのうち2つ、**「箇条書きを禁止する」「文字数を区切る（◯字以内）」という書式指定**を試しました。材料は[監視の対策は100件でも効く](/recipes/backlog-scale-holds-brevity-breaks-it/)と同じ架空の監視材料です。

試した条件は次の4つです。それぞれ、材料2本（SNS監視・問い合わせ監視）×各2回＝4回ずつ実行しました（計16回）。

- 対策の一文（「記録の日付が本日のものだけを新着として数えてください」）あり・箇条書き禁止
- 対策の一文あり・100字以内
- 対策の一文＋優先指定（「書式の指定より優先してください」）・箇条書き禁止
- 対策の一文＋優先指定・100字以内

正しい答えはどちらの材料でも「新着0件」です。

### 字数制限そのものが守られるかを確かめたい {: .trouble }

この記事の「100字以内」版（優先なし4回・優先あり3回・言い直し後4回）は、数字で答えた回がすべて49〜88字に収まりました。ただし、これは今回の材料・今回の回での結果です。項目数が増えて一覧が長くなったときに同じ字数で収まるかは、この記事では試していません。

### 過去分がもっと多い場合（数百件・数千件）は {: .trouble }

この記事が試したのは、前の2本と同じ過去分100件までです。数百件・数千件に増えた場合は、[前の記事](/recipes/format-break-did-not-return/)と同様にこの記事でも扱っていません。

## 応用・次の一手 {: .next }

**この記事の結論は2つです。**①「箇条書きを禁止する」「100字以内」という書式指定は、対策の一文の有無にかかわらず、数字で答えた14回すべてで新着件数を正しく保ちました。前の記事の「表形式」「絵文字」と同じく、「簡潔に」のような崩れ方は再現しませんでした。②優先指定を付けた2条件では、4回中1回ずつ、数字の代わりに確認が返りました。文面は「指示文の日付とシステムの日付が食い違っています」です。書式指定が原因の誤答ではなく、決め打ちの日付と実行環境の日付のズレに、AIが自分から気づいた結果です。

⚠️ **①から「書式指定は何を付けても対策を壊さない」とは言えません。**[前の記事](/recipes/format-break-did-not-return/)が書いているとおり、今回も「今回は崩れなかった」ことしか確かめていません。対策の一文を外す判断はしないでください。

📌 **②は、自分の環境で自動化を組むときに実際に関わってきます。**指示文に「今日は◯月◯日です」と決め打ちの日付を書くテンプレートを使うなら注意してください。実行環境の実際の日付と食い違う場面（テスト実行・時刻のずれた再実行など）で、AIが確認を挟んで止まることがあります。言い直し方の節にある1文を足すと、この記事の8回では確認待ちが0回になりました。

⚠️ **この記事が実測していないこと**は次の3つです。

- 「箇条書き禁止」「100字以内」以外の書式指定の組み合わせ
- 一覧が長くなったときに100字の制限自体が保たれるか
- 過去分が数百件・数千件とさらに多い場合

実際に監視対象を追加する人は、最初の1回だけ、報告された件数と元の一覧を自分の目で見比べてください。
