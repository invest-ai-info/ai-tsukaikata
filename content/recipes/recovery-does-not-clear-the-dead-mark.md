## これで何ができるか {: .what }

[死活判定は数字の選び方で変わる](/recipes/raw-count-catches-it-new-count-misses-it/)は、「取得件数」を渡せば健全な相手を誤判定しないことを確かめました。今回は一歩先です。<mark>取得件数と新着件数を両方渡せば、通知文を「取得自体ができない」「中身が止まっている」「正常」の3種類に書き分けられるかを試しました。</mark>

架空の監視ログ2本（情報源8つ・21日分と24日分）に、同じ基準を2つの言い方で当てました。結果は次の4つです。

1. **基準を明示した版**（「取得件数が3回連続0なら〜」と条件を数字で書く）は、2つの材料・各2回・合計32件の判定がすべて正解でした。健全・取得不可・停止の3種類とも、取り違えは0件です。
2. **基準をあいまいにした版**（数字の条件を書かず「判定してください」とだけ頼む）でも、2回とも16件が全部正解でした。<mark>両方の数字を渡せば、基準を細かく書かなくても書き分けられます。</mark>
3. ただし<mark class="warn">「3回連続0」という基準の書き方そのものに罠がありました。</mark>過去に3日だけ取得が止まり、その後8日間回復している相手を混ぜると、**基準を明示した版だけ**が2回とも「今も取得自体ができません」と誤報しました。
4. 原因は条件の書き方です。基準を**あいまいに戻す**か、「直近3回分」「表の末尾3行」と**言い直す**と、同じ相手は2回とも正しく「正常」に戻りました。

📌 **この記事の数字はすべて架空データでの実測です。**実在の個人・企業の情報は含みません。材料や仮説を知らない独立した新規会話で、**合計14回・判定120件**試しました。生の返りと機械照合は `docs/evidence/recovery-does-not-clear-the-dead-mark.md` に全文置いてあります。

## 前提 {: .need }

| | |
|---|---|
| かかる時間 | 20分 |
| 費用 | 無料。無料のチャットAIで足ります |
| 必要なもの | 複数の相手を定期的にチェックしている記録（取得件数と新着件数の両方が分かる形） |
| プログラミング | **不要**。記録の表をそのまま貼るだけです |

**取得件数と新着件数が何を指すかは**[死活判定は数字の選び方で変わる](/recipes/raw-count-catches-it-new-count-misses-it/)**と同じです。**取得件数はページから読み取れた記事の総数（更新が無くても0にはならない）、新着件数は前回チェックより増えた件数です。

材料は架空の監視ログ2本です。どちらも、健全な相手（更新頻度は毎日〜月1でまちまち）・本当に取得できない相手・取得はできるが中身が止まっている相手を混ぜています。1本目（21日分）には、さらに**過去に3日だけ取得が止まり、その後8日間回復している相手**を1つ加えました。

## うまくいかないときの言い直し方 {: .fix }

### 「3回連続0」は、過去の一時停止も拾って「今も止まっている」と誤報する {: .trouble }

ここまでは良い結果ばかりでしたが、材料に1つだけ相手を加えて試すと崩れました。加えたのは情報源Xです。**点検11〜13の3日だけ取得件数が0になり、点検14以降は点検21まで8日間ずっと回復しています。**新着も回復後に3回起きています。

指示文は実験1と同じ「取得件数が3回連続して0だったら『取得自体ができません』」のままです。Xを混ぜた9情報源で、同じ指示文を2回試しました。

**2回とも、Xに対して「取得自体ができません」が返りました。**

```
X: 取得自体ができません
```

**8日前に回復しているのに、今も死んでいる扱いです。**他の8情報源（P〜W）の判定は実験1と同じく2回とも全部正解だったので、崩れたのはXだけでした。

**なぜこうなるのか。**指示文の「取得件数が3回連続して0だったら」という書き方は、**記録期間のどこかで一度でも3連続0があればよい**とも読めます。AIはこの読み方どおりに、点検11〜13の3連続0を見つけて、それだけで「取得自体ができません」と判定しました。回復後の8日間を見落としたわけではなく、**条件の書き方が「今も止まっているか」ではなく「過去に止まったことがあるか」になっていたのが原因です。**

### 基準をあいまいに戻すと、同じ相手を正しく「正常」と判定した

<div class="prompt">次の表は、9つの情報源を毎日1回チェックする自動監視の記録です（点検1〜21は21日分）。「取得件数」はその回にページから読み取れた記事の総数です。「新着件数」は前回のチェックより後に増えた記事の数です。

この記録から、情報源ごとに次の3種類のどれかを判定してください。
- 正常
- 取得自体ができていない
- 取得はできているが中身の更新が止まっている

情報源ごとに1行で、判定とその根拠を書いてください。</div>

（上記の直後に、Xを混ぜた9情報源の取得件数の表と新着件数の表を両方そのまま貼った）

**2回とも、Xは「正常」と判定されました。**根拠も2回とも回復に触れています。

> X: 正常 — 取得件数は基本18だが点検11〜13の3回だけ0が連続し、点検14で18に復帰した一時的な障害。新着は障害前後を通じて点検2・5・8・15・18・21とおおむね3回おきに発生しており、取得・更新ともに継続している。

他のP〜W・S・Tも含めて2回とも9/9で全部正解です。<mark>数字の条件を外すと、AIは「今の状態」を自分で考えて判定し、過去の一時停止を取り違えませんでした。</mark>崩れていたのは基準をあいまいにしたことではなく、**基準を数字で明示したときの「3回連続」という書き方そのものでした。**

### 明示するなら「直近」を書く——「直近3回分」に言い直すと直る

## 応用・次の一手 {: .next }

**結論は、条件に「直近」という範囲の指定を必ず入れることです。**「3回連続して0」のような条件は、記録のどこで満たされてもよいと読まれる可能性があります。実務では、記録がどんどん伸びていく（毎日1行増える）ので、この読み方の違いは記事のテスト以上に効いてきます。

実際に運用するなら、絶対の点検番号（点検19・20・21）を指定できるとは限らないので、相対表現に直した版でも確かめました。

<div class="prompt">次の表は、9つの情報源を毎日1回チェックする自動監視の記録です。「取得件数」はその回にページから読み取れた記事の総数です（更新がなくても、記事がページに残っていれば0にはなりません）。「新着件数」は前回のチェックより後に増えた記事の数です。

次の基準で、情報源ごとに通知文を1行ずつ書いてください。
- 直近3回分（表の末尾3行）の取得件数が3回とも0だったら「取得自体ができません」という文にしてください
- 取得件数は0でない（取得はできている）のに、この記録期間の最初から最後まで新着件数が一度も1以上にならなかったら「取得はできていますが、中身の更新が止まっています」という文にしてください
- どちらにも当たらなければ「正常です」とだけ書いてください

情報源ごとに1行で、前置きやまとめは書かずに返してください。</div>

（上記の直後に、Xを混ぜた9情報源の取得件数の表と新着件数の表を両方そのまま貼った）

**こちらも2回とも9/9で全部正解でした。**絶対の点検番号を使わず「表の末尾3行」と書いても、Xは2回とも「正常です」に戻りました。この形なら、点検回数が増えても指示文を書き換える必要がありません。

この形は[毎日決まった時刻にAIを動かす仕掛け](/recipes/github-actions-daily-cron/)の通知判定にそのまま載せられます。閾値の決め方自体は[更新停止の異常判定は一律にしない](/recipes/flat-threshold-misfires/)、凍結の見抜き方は[自動化の凍結はAIが見抜く](/recipes/frozen-feed-does-not-go-unnoticed/)にあります。

⚠️ **この記事が実測していないこと**は2つです。

- 「中身が止まっている」側の基準（「記録期間の最初から最後まで新着が一度も無い」）にも、同じ「どこかで／直近で」の揺れがあるかどうか。今回の材料は、健全な相手の新着がどれも記録の途中に少なくとも1回は起きる形だったので、この軸は試していません
- 実際の点検回数が数百回に増えたとき（記録がもっと長くなったとき）に、「末尾3行」という相対表現が同じ精度で効くか

次に測るなら、「末尾3行」と「どこかで3連続」の2つの言い方を、点検回数を100件・300件と増やした材料で比べます。[見張りの対象を100件に増やしてもボロが出ないか](/recipes/backlog-scale-holds-brevity-breaks-it/)と同じ軸（規模を増やしたときに言い回しが保つか）の続きになります。
