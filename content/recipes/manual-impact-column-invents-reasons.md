## これで何ができるか {: .what }

毎月やっている作業を、他の人が代わりにできるようにマニュアル化したい。引き継ぎでも、外部に発注するときの説明でも、よく出てくる場面です。自分で書くと迷う点が1つあります。<mark>「申請が要る」「一応そういうルールがある」程度のさりげない注意点は、きれいなマニュアルに変換する過程で消えないでしょうか</mark>。

先に結果を書きます。<mark>この心配は杞憂でした。</mark>架空の月次作業の説明文（請求書発行・4つの細則入り）を3回変換したところ、細則は**3回とも全部**マニュアルに残りました。ところが別の心配が実際に当たりました。手順表に「この手順をやらないとどうなるか」の列を足すと危険です。<mark class="warn">理由が書いていない手順に、作り話の理由が付きます</mark>。<mark class="warn">回ごとに違う理由が、3回とも全部付きました。</mark>1文を足すだけで、この作り話は0件に直ります。

<figure class="figure">
<img src="/static/images/manual-stated-vs-unstated.svg" alt="同じ説明文の中にあるルールを、理由が書いてあるものと、ルールがあるとだけ書いてあるものに分けた図。左の緑の枠「理由も書いてある（1つ）」には「月の最終営業日は15時までに作業を終える」が入り、下に「本文に理由が明記されている：15時以降はシステムがメンテナンスで使えなくなる」と注記がある。右の枠「ルールがあるとだけ書いてある（4つ）」には、初回ログインの上長申請、20万円超の経理部長確認、控えのフォルダ保存、控えのSlack投稿の4つが入り、理由は書かれていない。下の注記には、『やらないとどうなるか』と聞くと右の4つのうち3つ（確認メール以外）に本文には無い組織的な理由が作られたこと、左の1つは本文のまま正しく書けたことが書かれている。">

この記事は、架空データで**6通りの頼み方・計13回**を試した結果から書いています。安全に使える言い方と、避けるべき言い方を分けて渡します。

## 前提 {: .need }

| | |
|---|---|
| かかる時間 | 15分 |
| 費用 | 無料。無料のチャットAIで足ります |
| 必要なもの | ブラウザで使えるAI（ChatGPT・Claude・Geminiなど）と、自分がやっている作業の説明 |
| プログラミング | **不要**。自分の作業をそのまま書いて貼るだけです |

説明は箇条書きでなくて構いません。実際に試したのも「だいたい決まっていて、まず◯◯して…」という、話すときのままの文章です。

## AIへの頼み方 {: .ask }

### 1. まず、そのまま変換を頼む

<div class="prompt">下に書くのは、私が毎月やっている作業です。他の人が代わりにできるように、手順のマニュアルにしてください。

（やっている作業をそのまま書く。きれいにまとめなくてよい）</div>

**3回試して3回とも**、文章の中にさりげなく混ぜた細則が全部マニュアルに反映されました。仕込んだのは次の4つです。

- 初回だけ要る承認
- 金額が大きいときだけの確認
- 控えの保存先が2か所あること
- 月末だけの制限

<mark>書き方を整えても、書いてある事実は消えません</mark>。まず安心して、このまま試してください。

### 2. 「初めての人」と「毎月やっている人」で分けて抜き出す

引き継ぎ資料として使うなら、整理のされ方まで一歩進めます。

<div class="prompt">下の文章を手順のマニュアルにしてください。変換する前に、本文の中にある「初めてやる人にだけ必要なもの（申請・承認・初回だけの準備）」と「毎月やっている人には当たり前すぎて書いていないこと」を、それぞれ別の見出しでまず全部抜き出してください。そのあと、残りの作業を手順としてマニュアルにしてください。

（やっている作業をそのまま書く）</div>

<mark>「初めての人」と「毎月やっている人」で分けて抜き出させても、残る情報の量は1と同じでした</mark>。漏れを防ぐ効果があったわけではありません。効くのは整理の質のほうです。「初回だけ必要なもの」が独立した見出しになるので、担当が替わるときに最初に読む場所がはっきりします。

### 3. ⚠️ 「やらないとどうなるか」の列は、理由が無いと作り話になる

ここからが本題です。手順を表にするとき、重要度が分かるように列を足したくなります。

<div class="prompt">下に書くのは、私が毎月やっている作業です。番号付きの手順表にしてください。各手順には「この手順をやらないとどうなるか」の列も付けてください。

（やっている作業をそのまま書く）</div>

<mark class="warn">「やらないとどうなるか」の列をそのまま使うのは危険です。</mark>本文に理由が書いてある手順（月末のシステムメンテナンスで使えなくなる、など）は正しく書けました。ところが、**本文には「そういうルールがある」とだけ書いてあって理由が書いていない手順**が3つあります。控えをSlackに貼る・控えをフォルダに保存する・件名を統一する、の3つです。この3つには、**3回とも全部**、本文のどこにも無い説明が付きました。

<figure class="figure">
<img src="/static/images/manual-reason-fabrication.svg" alt="手順表に「やらないとどうなるか」列を足す頼み方を2条件で試し、本文に理由が書かれていない3手順（件名の統一・控えのフォルダ保存・Slackへの投稿）について、作り話の理由が付いたか「書かれていません」と正直に書いたかを、5回ぶん並べた表。条件A（そのまま列を足した3回）は、3手順とも3回とも全部「作り話」。条件B（『書かれていなければ理由は書かれていませんと書いて』を足した2回）は、3手順とも2回とも全部「書かれていません」。下の注記には、条件Aの作り話はSlack投稿の理由だけでも回ごとに中身が違う3通りの説明文になったこと、条件Bは9マスとも作り話が0件で、理由が書いてある1手順（月末メンテナンス）だけは本文のとおりに正しく書いたことが書かれている。">
<figcaption>理由が書いていない3手順は、3回とも全部作り話になりました。</figcaption>

特に分かりやすいのが「控えをSlackに貼る」の行です。3回とも理由が付きましたが、**中身は毎回違いました**。出てきた理由は3通りです。

- ダブルチェックの機会を失う
- 他の担当者が進捗を把握できない
- リアルタイムで共有できない

本文にある理由なら毎回同じ言葉になるはずです。<mark>回ごとに言い方が変わる理由は、作り話だという証拠そのものです</mark>。この表をそのまま社内に配ると危険です。<mark class="warn">誰も言っていない「組織の方針」が、さも決まっていたことのように広まります</mark>。

## うまくいかないときの言い直し方 {: .fix }

### 「やらないとどうなるか」の列を、作り話にせず使いたい {: .trouble }

列を足したいだけなら、受け皿を1文足すだけで直ります。

<div class="prompt">下に書くのは、私が毎月やっている作業です。番号付きの手順表にしてください。各手順には「この手順をやらないとどうなるか」の列も付けてください。理由が本文に書かれていない手順については、理由を考えて埋めずに「理由は書かれていません」としてください。

（やっている作業をそのまま書く）</div>

**2回試して2回とも**、理由が書いていない3手順は全部「理由は書かれていません」に変わりました（9マス中0件）。理由が書いてある手順（月末メンテナンス）だけは、2回とも本文どおりの説明が正しく残りました。<mark>「無ければそう言ってください」の一文が、作り話と事実を仕分けます</mark>。

### 列を足した表を、もう作ってしまったあとに気づいた {: .trouble }

先に3のまま使ってしまった場合も、あとから回収できます。

<div class="prompt">下の表は、私が書いた作業説明の文章から、あなたが作った手順表です。各行の「やらないとどうなるか」の説明について、元の文章のどこに書いてあるかを示してください。元の文章に書かれていないものは、正直に「書かれていません」と言ってください。

（元の文章と、できあがった手順表を貼る）</div>

**1回試して**、4行すべてで正しい自己訂正が返りました。理由が本文に無い3行は「書かれていません」、理由が本文にある1行は「書かれています」。引用した場所まで示した上で、そう言い直しました。<mark>作ってしまったあとでも、出典を聞けば自分で見分けます</mark>。

### 自分では気づかなかった抜けが心配 {: .trouble }

列を足さなくても、違う聞き方で抜けを探せます。

<div class="prompt">下に書くのは、私が毎月やっている作業です。他の人が代わりにできるように、手順のマニュアルにしてください。作ったあとに、自分で見直して、実際にやる人が困りそうな抜けがあれば追記してください。</div>

この聞き方で返ってきた追記には、2つの例がありました。「承認を出す上長の名前・連絡先を書いてください」「確認メールの宛先や保管場所を決めておくと迷いません」です。<mark>追記された2つの例は、どちらも具体的な値を作らずに「ここは自分で埋める欄です」と示す形でした。</mark>これは3の作り話とは違います。欄を作るだけで、中身までは作っていません。思い込みで「たぶん動きます」と言わせないための基本は[「たぶん動きます」と言わせないための頼み方](/recipes/verify-before-report/)にまとめてあります。

## 応用・次の一手 {: .next }

マニュアルができたら、次にやるべきことは2つあります。

まず、**自分では気づかない穴があるかを、実行させて確かめる**ことです。マニュアルは書いた本人には足りて見えますが、初めてやる人の目には足りません。

<div class="prompt">このマニュアルを、初めて読む人として、書かれているとおりにだけ実行してください。できないところがあったら、そこで止まって理由を書いてください。自分で決めて先に進まないでください。</div>

このやらせ方の詳しい理由は[手順書は、読み直すより「そのとおりにやらせて」穴を見つける](/recipes/try-the-runbook/)にまとめました。

もう1つ、作業を毎月続けるなら、メモを溜めて月1回見直す形に進められます。

<div class="prompt">この作業を、毎回やるたびに気づいたことをメモしておいて、月1回あなたに見せて見直してもらう形にしたいです。私はプログラムを書けません。私がやる作業を番号を振って教えてください。作れるものはあなたが作ってください。</div>

試したところ、**コピー＆ペーストだけで回る運用**が返ってきました。マニュアルの末尾に「気づきメモ」欄を追加し、作業のたびに1行メモを足し、月末にまとめて見直しを頼む、という形です。具体的な値を勝手に作ることもありませんでした。まずはマニュアルを1本作って、[そのとおりにやらせて穴を見つける](/recipes/try-the-runbook/)ところから始めてください。
