## これで何ができるか {: .what }

[更新停止の異常判定は一律にしない](/recipes/flat-threshold-misfires/)は、週1回・月1回・隔週とばらばらな**3系統**の監視対象を扱いました。そこで確立したのが、「相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を基準にする」という指示文です。<mark>今回確かめたのは、同じ指示文を監視対象**12・20系統**に増やしても、相手ごとの計算が崩れないかです。</mark>プログラミングは要りません。

架空の更新履歴を12系統・20系統の2段階で用意しました。混在させたのは週1回・隔週・月1回・不定期（間隔が長い相手）の4種類です。あいまいな境界には置かず、2種類だけを仕込みました。

- **真に異常な相手**＝過去最大の間隔の1.5倍以上止まっている
- **真に正常な相手**＝過去最大の間隔+5日以内

同じ指示文を、並び順を変えた版も含めて計10回試しました。

1. **12系統（並び順を変えた2通り×各2回＝4回）は、真の異常4件・真の正常8件を、4回とも1件の誤りもなく判定しました。**
2. **20系統（2回）も、真の異常7件を7件とも見逃しませんでした。**
3. <mark>ただし20系統では、基準をわずかに超えた1系統（真値は正常。過去最大の間隔+4日の超過）を、2回とも誤って「異常」と判定しました。</mark>これは曖昧な言葉（「数日の余裕」）の解釈が、相手が増えて境界ケースに実際に当たったことで表面化したものです。
4. 親記事の言い直し方（基準まであと3日以内を「黄信号」にする）を、そのまま当てました。すると、この1系統は2回とも黄信号に動かず、異常のまま残りました。**この言い直し方は、まだ基準に達していない側にしか効きません。**

📌 **この記事の実測はすべて架空データです。**材料や仮説を知らない独立した新規プロセス（`claude --safe-mode --tools ""`）で試しました。回数は合計**14回**です（12系統10回＋20系統の各条件2回×2通り）。生の返りと機械照合は `docs/evidence/yellow-signal-misses-the-already-crossed.md` に全文置いてあります。

## 前提 {: .need }

| | |
|---|---|
| かかる時間 | 15分 |
| 費用 | 無料。無料のチャットAIで足ります |
| 必要なもの | 監視している複数の相手の、過去の更新日付（日付だけの一覧） |
| プログラミング | **不要**。文章を貼って指示文を添えるだけです |

この記事は、[更新停止の異常判定は一律にしない](/recipes/flat-threshold-misfires/)が確立した「相手ごとに基準を計算する」という考え方そのものには触れません。**監視対象の数が増えたとき、その考え方が同じ精度で動くか**だけを確かめます。まだあちらを読んでいない場合は、先にそちらで基本形を確認してください。

監視対象が1つだけで、正常な間隔が固定で決まっている場合は別です。その場合は[止まったフラグを自動で解除する](/recipes/stuck-flag-proceed-verdict/)のような固定の閾値のほうが向いています。

## AIへの頼み方 {: .ask }

### 1. 12系統に増やして、同じ指示文を試す

材料は、週1回・隔週・月1回・不定期（間隔が長い相手・荒い相手）を混ぜた12系統の更新履歴です。今日の日付は2026-10-19です。

```
① 社内Wikiの更新通知（週1回配信）
2026-08-31
2026-09-07
（…中略。全文は docs/evidence/yellow-signal-misses-the-already-crossed.md）
2026-10-12（最終更新）

② 競合サイトの価格ページ監視（週1回想定）
（以下、③〜⑫も同じ形で続く）
```

<div class="prompt">毎日、この12の相手の更新を自動でチェックしています。相手ごとに更新の頻度もばらつき方も違うので、異常の基準を1つの日数に決め打たないでください。相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を「これを超えたら異常」の基準にしてください。今日時点で異常(更新が止まっている)と言える相手を①〜⑫の中からすべて挙げ、判定に使った基準の日数も相手ごとに書いてください。</div>

**2回とも、真の異常4件を1件の漏れも誤りもなく挙げました。**例えば、週1回のはずなのに15日止まっている相手も、隔週のはずなのに33日止まっている相手も、両方拾っています。基準は「過去の最大間隔+3日」と、自分から数字を決めています。「数日」という曖昧な言葉を、2回とも同じ3日に落ち着けた点も安定していました。

**なぜこの言い方か。**親記事と同じ指示文を、材料の規模だけ4倍（3→12系統）にしています。言い方を変えずに規模だけ動かすことで、「計算の仕組みそのものが規模に耐えるか」を切り分けられます。

### 2. 並び順を変えても、同じ4件が挙がるか

同じ12系統を、並び順だけ変えた材料に差し替えました（内容は同一・①〜⑫の数字の割り当てだけが変わっています）。指示文1と一字一句同じものを、もう一度貼ります。

<div class="prompt">毎日、この12の相手の更新を自動でチェックしています。相手ごとに更新の頻度もばらつき方も違うので、異常の基準を1つの日数に決め打たないでください。相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を「これを超えたら異常」の基準にしてください。今日時点で異常(更新が止まっている)と言える相手を①〜⑫の中からすべて挙げ、判定に使った基準の日数も相手ごとに書いてください。</div>

**2回とも、番号は変わっても「相手」としては同じ4件を正しく挙げました。**長い一覧の**どこに**異常な相手が置かれていても、判定の精度は変わりませんでした。長い一覧は後半ほど扱いが雑になるという心配は、この規模（1回の依頼に12件をまとめて渡す形）では当たりませんでした。

### 3. 20系統まで増やすと、どこかで崩れるか

12系統の2倍近い20系統まで増やしました。真に異常な相手は7件、真に正常な相手は13件です（うち1件だけ、基準を4日だけ超える境界ケースにしてあります）。同じ指示文を、①〜⑳に書き換えて試します。

<div class="prompt">毎日、この20の相手の更新を自動でチェックしています。相手ごとに更新の頻度もばらつき方も違うので、異常の基準を1つの日数に決め打たないでください。相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を「これを超えたら異常」の基準にしてください。今日時点で異常(更新が止まっている)と言える相手を①〜⑳の中からすべて挙げ、判定に使った基準の日数も相手ごとに書いてください。</div>

**2回とも、真の異常7件は7件とも見逃しませんでした。**その一方で、<mark class="warn">基準を+4日だけ超えた境界ケース（真値は正常）を、2回とも異常側に誤って判定しました。</mark>基準は今回も「最大間隔+3日」で、境界ケースは+4日の超過なので、このルールどおりなら異常判定自体は筋が通っています。問題は、この相手を人間がどちらに置きたいかという、ルールの外側の話です。

## うまくいかないときの言い直し方 {: .fix }

### 「黄信号」を足しても、わずかに超えた相手は拾えない {: .trouble }

親記事では、境界に近い相手を「異常」と「正常」の間に置く言い方（黄信号）が効きました。これを20系統にそのまま当てます。

<div class="prompt">毎日、この20の相手の更新を自動でチェックしています。相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を「異常」の基準にしてください。ただし、基準まであと3日以内に迫っているものは「異常」ではなく「黄信号(要注意)」として、はっきり異常なものとは分けて教えてください。①〜⑳それぞれの信号(正常・黄信号・異常)を、基準日数とあわせて教えてください。</div>

**2回とも、境界ケースは黄信号に動かず、異常のまま残りました。**返り自身も、境界に近いことを認識していました。「基準を1日だけ超えています」「余裕を4日にすると正常扱いになるので、確認の優先度は他より低めです」と書いています。認識しているのに、黄信号という**用意した受け皿には入りませんでした**。

**なぜ入らないか。**この言い方の「黄信号」は「基準まであと3日以内＝まだ超えていない」という条件です。境界ケースは**すでに超えている**ので、この条件に当たらず、素通りして異常側に落ちます。<mark class="warn">黄信号は、近づいている側にしか効かない受け皿でした。</mark>

### 「差が3日以内」と、両側を名指しする {: .trouble }

「まだ超えていない」ではなく、「超えたかどうかを問わない」差の大きさで黄信号を定義し直します。

<div class="prompt">毎日、この20の相手の更新を自動でチェックしています。相手ごとに、過去の間隔の最大値に数日の余裕を足した日数を「異常」の基準にしてください。ただし、経過日数と基準日数の差が3日以内のもの(まだ超えていないが迫っている場合も、わずかに超えた場合も両方)は「異常」ではなく「黄信号(要注意)」として、はっきり異常なものとは分けて教えてください。①〜⑳それぞれの信号(正常・黄信号・異常)を、基準日数とあわせて教えてください。</div>

**2回とも、境界ケースが正しく黄信号に動きました。**しかも、真の異常7件はそのまま異常に残り、明確な正常8件もそのまま正常に残っています。1か所だけ直って、他が崩れることはありませんでした。

<figure class="figure">
<img src="/static/images/yellow-signal-one-sided.svg" alt="黄信号の受け皿が片側版では拾えず両側版だと正しく拾うことを示す数直線の図。横軸は経過日数マイナス基準日数で、0が基準そのもの。片側版の帯は、マイナス3未満が正常、マイナス3から0未満が黄信号、0以上が異常。境界ケースはプラス1の位置にあり、片側版では0以上の異常の帯に入ってしまう。両側版の帯は、マイナス3未満が正常、マイナス3からプラス3までが黄信号、プラス3超が異常で、境界ケースのプラス1の位置は黄信号の帯の中に正しく入る。">
<figcaption>片側版は「超えた側」を素通りさせます。両側版は、同じ境界ケースを正しく拾います。</figcaption>
</figure>

**なぜこの言い方が効くか。**「あと3日」は時間の向き（まだ来ていない未来）を指す言葉で、超えた後の話とは馴染みません。「差が3日以内」は向きを持たない量なので、基準の手前・直後のどちらも同じ条件で拾えます。<mark>境界の受け皿を作るときは、近づいている側だけでなく、わずかに超えた側も同じ言葉で指定してください。</mark>

## 応用・次の一手 {: .next }

**この記事の値打ちは、次の2つを両方確かめたことです。**

- **安心材料**＝相手が増えても計算は崩れない
- **別の注意点**＝増えた分だけ境界ケースに当たりやすくなる

計算そのものを疑う前に、まず「数日」のような曖あいな言葉がどこかにないかを探してください。

📌 **参考までに、「数日」を具体的な数字「3日」に書き換えても結果は変わりませんでした**（1回の確認です）。繰り返した2回は使っていません。ツールを使えない設定なのに、呼び出しの形だけが返る壊れ方をしたためです。

<div class="prompt">毎日、この20の相手の更新を自動でチェックしています。相手ごとに、過去の間隔の最大値に3日を足した日数を「基準」にしてください。経過日数と基準日数の差が3日以内のもの(超えたかどうかを問わない)は「黄信号(要注意)」、差が+3日を超えたものは「異常」、それ以外は「正常」としてください。①〜⑳それぞれの信号を、基準日数とあわせて教えてください。</div>

結果は、両側版（指示文5）とまったく同じ赤7・黄5・緑8でした。曖昧な言葉を具体的な数字に置き換えることは、少なくとも損にはならないと見ています。

毎日ひとりでに回すなら、[毎日決まった時刻にAIを動かす](/recipes/github-actions-daily-cron/)の形に載せて、両側版の黄信号を保存版にするのがおすすめです。監視対象がさらに増えて、一覧そのものが読みづらくなってきたら別の記事も確認してください。[見張りの対象を100件に増やしてもボロが出ないか](/recipes/backlog-scale-holds-brevity-breaks-it/)が参考になります。

⚠️ **今回の20系統・計4回という規模での確認です。**監視対象が50件・100件まで増えたときに、境界ケースへの当たりやすさがどう変わるかはまだ確かめていません。相手の数が増えるほど、境界ケースに遭遇する機会そのものが増える点は、見張る相手を増やすときに覚えておく価値があります。
