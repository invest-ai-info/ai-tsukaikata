## これで何ができるか {: .what }

<mark>AIの「できました」が、本当に動くものになります。</mark>

AIに何かを作らせると、かなりの確率でこう返ってきます。

- 「実装しました。おそらく正常に動作します」
- 「設定は正しいはずです」
- 「こちらのURLから取得できます」

どれも<mark class="warn">実際には一度も動かしていない状態で書かれています</mark>。しかも文章は自信たっぷりなので、読んだ側は完成したと思ってしまいます。

この記事は、他の記事で作った仕組みを通じて<mark>一番効いた指示だけを集めたもの</mark>です。新しい道具はいりません。**言い方を変えるだけ**です。

実際にあった例を1つ。[AIの最新情報を自動で集める](/recipes/ai-news-auto-collect/) を作ったとき、AIは追跡先のRSSのURLを一覧で出してきました。そこで「実際に開いて確認して」と付け足したところ、Anthropicの公式ニュースはRSSを出しておらず、**試した3つのURLが全部404**だと分かりました。<mark class="warn">聞かなければ、存在しないURLを見に行く仕組みが完成していました。</mark>エラーも出ません。ただ静かに、何も集まらないだけです。

## 前提 {: .need }

| | |
|---|---|
| かかる時間 | 5分 |
| 費用 | 無料 |
| 必要なもの | **実際に動かせるAI**（コマンドを実行できる、Webを見に行ける） |
| プログラミング | **不要** |

<mark class="warn">ここだけは注意してください。</mark>チャット画面しかないAIには、この記事の指示は効きません。「実際に開いて確認して」と頼んでも、開く手段が無いからです。開いたつもりの報告が返ってくるだけで、かえって危なくなります。手元で動かせるAI（Claude Code のような、ファイルを触れてコマンドを打てるもの）が前提です。

## AIへの頼み方 {: .ask }

### 1. 「たぶん」を禁止する

これが基本形で、一番短く、一番効きます。

<div class="prompt">「たぶん」ではなく、実際に動かして確かめてください。
確かめていないことは「確かめていない」と書いてください。</div>

<mark>後半が本体です。</mark>前半だけだと、AIは確かめずに「確かめました」と書けてしまいます。「確かめていないと書いていい」と許可を出すと、正直な報告が返るようになります。

### 2. 実在するかどうかを、開いて確かめさせる

URL・ファイル名・設定項目・オプション名。この4つは、AIが最も自信たっぷりに存在しないものを書いてくる場所です。

<div class="prompt">ただし、実際にそのURLにアクセスして、本当に中身が返ってくるか1件ずつ確認してからリストにしてください。開けなかったものはリストに入れず、「開けなかった」と報告してください。</div>

<mark>「1件ずつ」と「報告してください」を必ず入れてください。</mark>まとめて確認させると代表1件だけ見て済ませます。報告を求めないと、落としたことを黙って処理します。

### 3. わざと壊して、検知できることを確かめさせる

監視やチェックの仕組みを作らせたときは、これを付けないと意味がありません。

<div class="prompt">実行する前に、この監視が本当に異常を検知できるか確かめたいです。

わざと異常な状態を作って（存在しないページを見に行かせる、古い日付を渡す、など）、ちゃんと検知して通知が飛ぶところまで確認してください。

「検知できるはずです」ではなく、実際に動かして確かめてください。</div>

異常を検知する仕組みは、**平常時は何も起きないのが正常**です。つまり<mark class="warn">壊れていても、動いているように見えます</mark>。作った直後にわざと壊してみるのが、唯一の確認方法です。詳しくは [静かに壊れたのを見つけさせる](/recipes/auto-health-check/) に書きました。

### 4. 出来上がったものの現物を見せさせる

「良くなりました」と言われたら、必ずこれを返します。

<div class="prompt">実際に生成されたものを3件見せてください。そのうえで、どこを直せば良くなるか案を出してください。いきなり直さず、案を見せてください。</div>

<mark>3件という数字に意味があります。</mark>1件だと、たまたま上手くいったものを選んで見せられます。3件出せば、平均的な出来が見えます。

### 5. 資料と実物が食い違ったら、実物を優先させる

AIは、渡した資料やメモを事実として扱います。資料のほうが古くなっていても気づきません。

<div class="prompt">メモや資料に書いてあることは、書いた時点のスナップショットです。

ファイル名・設定値・手順を使うときは、そのまま信じずに、実物を確認してから使ってください。食い違っていたら実物を優先して、資料のほうを直してください。</div>

これを言っておかないと、<mark class="warn">半年前の設定値を今の事実として扱われます</mark>。

### 6. 推測と実測を、書き分けさせる

長い作業になるほど、報告の中に推測が混ざってきます。

<div class="prompt">報告するときは、実際に確かめたことと、そう考えた理由を分けて書いてください。

確かめたことには、何をどう確かめたかを添えてください。確かめていないことは「未確認」と書いてください。</div>

<mark>「どう確かめたか」を書かせると、確かめていない場合に書けなくなります。</mark>ここで手が止まるので、実際に確かめに行きます。

## うまくいかないときの言い直し方 {: .fix }

### 「できました」と言われたのに動かない {: .trouble }

一番よく起きます。そして一番危ない返事です。

<div class="prompt">いま「できました」と言いましたが、実際に動かして確認しましたか。

していないなら、そう言ってください。そのうえで、いま動かして結果を見せてください。</div>

<mark>責めずに、逃げ道を先に用意するのがコツです。</mark>「していないなら、そう言ってください」があると、素直に「していません」と返ってきます。

### 原因を推測で語り始める {: .trouble }

「動かなかった」とだけ伝えると、AIはもっともらしい原因を並べ始めます。

<div class="prompt">推測で原因を挙げる前に、実行履歴とエラーメッセージの現物を見せてください。

事実を確認してから、原因の話をしましょう。</div>

<mark>事実を見せてから話させる</mark>と、推測の量が激減します。順番を変えるだけです。

### 「確認しました」の中身が分からない {: .trouble }

<div class="prompt">確認したとのことですが、具体的に何をどう確認しましたか。

実行したコマンドと、返ってきた出力をそのまま見せてください。</div>

出力をそのまま求めると、確認していない場合はここで止まります。<mark class="warn">要約させると、確認していなくても書けてしまいます。</mark>

### 一度は確かめたのに、次から元に戻る {: .trouble }

毎回言うのは続きません。仕組みに移します。

<div class="prompt">「動かして確かめてから報告する」を、この先ずっと守ってほしいです。毎回言わなくて済むように、覚えておく形にしてください。</div>

やり方は [AIに記憶を持たせる](/recipes/claude-code-memory/) に書きました。ただし記憶は「お願い」なので、破れます。本当に守らせたいなら次の節へ進んでください。

### 存在しないものを、自信たっぷりに書いてくる {: .trouble }

<div class="prompt">分からないことは「分からない」と答えてください。

もっともらしい答えを作るより、分からないと言われるほうが助かります。推測で答える場合は、必ず「推測ですが」と付けてください。</div>

<mark>「そのほうが助かる」と伝えるのが効きます。</mark>AIは役に立とうとして埋めにきます。空欄のほうが役に立つと分かれば、埋めなくなります。

## 応用・次の一手 {: .next }

**まず1と2だけ試してください。**「たぶんではなく実際に動かして確かめて」と「実際に開いて確認して」の2つで、大半は防げます。

慣れてきたら、**言葉ではなく仕組みで止める**ほうへ移してください。

<div class="prompt">いまのルールは、うっかり破れてしまいます。破れないように、機械的にチェックして止める仕組みを作ってください。</div>

言葉での指示は「お願い」ですが、仕組みは「保証」です。[定時実行を任せる](/recipes/github-actions-daily-cron/) と [静かに壊れたのを見つけさせる](/recipes/auto-health-check/) は、どちらも「気をつける」ではなく「気をつけなくても壊れない」形にしてあります。

最後に、この記事を書いている最中に実際に起きたことを1つ。追跡先を新しいサービスへ移すとき、設定に書く名前を「たぶんこれだろう」で書きかけました。念のため実際に一覧を取得して確かめたところ、**予想した名前は存在しませんでした**。そのまま書いていたら、エラーも警告も出ず、ただ静かに0件を返し続ける設定が出来上がっていました。

<mark class="warn">一番怖いのは、間違いがエラーとして現れないことです。</mark>確かめる一文は、そのために足します。
