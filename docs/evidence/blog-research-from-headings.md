5. queue.txt の書式

  ・文字コードは UTF-8、改行は LF で保存してください（Windows のメモ帳だと CRLF になりがちで、キーワード末尾に見えない文字が混ざります）

  ・空行と、# で始まる行はコメントとして読み飛ばしてよいか
  ・1回の実行で何件処理するか（全部か、上から N 件か）。件数が増えると実行時間と料金が伸びます
  ・同じキーワードを毎日回したい場合はどうするか（済にすると翌日走りません。毎日回す用の別ファイルが要ります）

6. results のファイル名

  ・「日付-キーワード.txt」のキーワード部分に / : ? * 空白 などが入ると、そのままではファイル名にできません。
    置き換えルールを決めてください（推奨: 空白と記号は _ に置換、長さは50文字までで切る）
  ・日付は何時基準か。Actions は UTC で動くので、JST の日付を使うなら明示指定が要ります
  ・追記時に、区切り（実行時刻の1行）を入れてよいか
    → 指示文は「1行目からいきなり始めて」なので、AIの出力自体には前置きを入れさせず、
      区切り行はスクリプト側で足す、という切り分けにするのが安全です

7. 時刻

  ・毎朝7時 = JST 7:00 は UTC 22:00（前日）です。cron は `0 22 * * *` になります
  ・GitHub の cron は数分〜数十分遅れることがあります。7:00ちょうどの保証は取れません
  ・リポジトリが60日間更新されないと schedule は自動停止します（毎日コミットが入るので実質問題になりません）

8. 失敗したときの残し方

  ・失敗ログの置き場所（例: logs/YYYY-MM-DD.log）と、そこに何を残すか
    → 行番号・キーワード原文・失敗した工程（見出し取得 / AI呼び出し / 書き込み）・終了コード・エラー本文の先頭数行
  ・失敗した行は済にしない（翌日また拾う）でよいか。それとも "FAIL " の印を付けて止めるか
  ・失敗しても残りの行は続けるか、そこで全部止めるか
  ・気づく手段が要るか（そのまま放置だと誰も見ません）。Issue を自動で立てる / メール / Slack の Webhook URL のいずれか
  ・リトライを何回するか（API の一時的なエラーは1〜2回の再試行で大体通ります）

◆ 指示文の固定について（こちらで気をつける点）
──────────────────────────────────────────

  ・指示文はスクリプト内にヒアドキュメントで置き、変数展開を止めた形（<<'PROMPT' … PROMPT）にします。
