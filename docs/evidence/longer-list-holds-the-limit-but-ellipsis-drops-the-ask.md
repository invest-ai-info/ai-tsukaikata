# 試した証拠 — longer-list-holds-the-limit-but-ellipsis-drops-the-ask

[書式をあと2種変えても対策は効く](/recipes/more-formats-hold-but-a-date-mismatch-stalls-it/)の著者自身が残した
未測定事項（記事内「字数制限そのものが守られるかを確かめたい」節）＝
「項目数が増えて一覧が長くなったときに同じ字数で収まるかは、この記事では試していません」を実測した。

材料は[監視の対策は100件でも効く](/recipes/backlog-scale-holds-brevity-breaks-it/)と同じ
架空の2系統（SNS監視・問い合わせ監視）を使い、**監視対象の件数そのものを3件→12件に増やした**
（backlog-scale記事は1対象の過去分件数を増やしたが、今回は監視対象の数を増やした点が違う）。

各系統に「最新の件名/タイトルをそのまま書くと100字を超える」項目を2つ仕込んだ（早い位置・遅い位置に1つずつ）。
3件版にはそのうち早い位置の1つだけを含めた。

- SNS監視・長い一覧（12件）：公式Instagram（2番目）・公式メルマガ案内（10番目）が仕込み項目
- SNS監視・短い一覧（3件）：公式Instagram（2番目）が仕込み項目
- 問い合わせ監視・長い一覧（12件）：返品・交換フォーム（2番目）・採用に関する問い合わせ（10番目）が仕込み項目
- 問い合わせ監視・短い一覧（3件）：返品・交換フォーム（2番目）が仕込み項目

実行は、文脈を持たない新規のClaude（Agent機能・subagent_type: general-purpose）に、指示文と教材だけを渡し、
「一般的なチャットAIとして自然に返答する」よう頼んで得た。本実験の仮説（一覧が長いと崩れるか）は
実行役には伝えていない。

判定は、返ってきた各行の文字数をPythonの`len()`で数え、100字超の有無・項目の欠落・「…」による
文中途切れの有無を機械で確認した（下の「照合（機械）」節）。

## 全体のまとめ（機械集計）

| 条件 | 行数 | 100字超 | 「…」による中途切断 |
|---|---|---|---|
| 短い一覧（3件）×2系統×2回＝12行 | 12 | 0 | 1（SNS2回目） |
| 長い一覧（12件）×2系統×2回＝48行 | 48 | 0 | 2（問い合わせ1回目の2項目） |
| 言い直し後・長い一覧×2系統×2回＝48行 | 48 | 0 | 0 |

要約が必要だった項目（新着1件以上で、原文が100字を超える）は12回の実行中12件。
うち3件（25%）が「…」で途中に切れ、3件とも切れた位置は具体的な依頼内容（質問）が
まだ述べられていない場所だった。言い直し後は同条件（長い一覧2系統×2回＝要約対象4項目×2回＝実質8項目）で
「…」は0件だった。

## この記事から出た教訓（`content/_lessons.md` へ）

1. 一覧の長さ（3件→12件）そのものは、1行の字数制限を破る原因にならなかった
   （台帳の既存の型＝「件数の規模そのものは崩れの原因になりにくく、書式指定のほうが崩れを引き起こす」の再発。
   新規番号は立てず、既存の型の再発として記録する）。
2. 🆕 **字数制限を守るための圧縮の「やり方」が回によって割れる。**同じ材料・同じ指示文でも、
   ある回は内容を保って要約し、別の回は文中を「…」で切って終える。切る場合、切れる位置は
   「まだ要点（質問の中身）を言っていない場所」になりやすく、字数は守られていても
   読者が受け取る情報はゼロに近い。「…で切らず、要約して言い切って」と1文足すと、
   同条件で再現しなかった（8項目中0件）。
