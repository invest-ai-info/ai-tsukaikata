貼っていただいた記録で、いちばん重要なのは「書かれていること」ではなく「書かれていないこと」です。

## 記録には 8/19 の行がありません

14行ぶん（8/5〜8/18）が並んでいて、今朝 8/19 の行が1行もありません。つまりこの記録の上では、**今朝は収集そのものが走っていない**（少なくとも、走った記録が残っていない）ということになります。

これが分かると、原因の候補をかなり絞れます。

**「新着が0件だったからメールが来なかった」ではありません。** 8/14 がちょうどその例で、新着0件・メールなしでしたが、行そのものは「完了 13件 0件 なし」として残っています。正常に走って送るものが無かった日は、必ず足あとが残る。今朝はその足あとが無いので、止まっているのはメールを送る手前ではなく、**もっと前の「起動」の段階**です。

同じ理由で、次の2つも今回の原因からは外れます。

- 収集先のサイト側の不調（取得件数は11〜15件で安定していて、じわじわ減るような兆候もありません）
- メール送信の失敗（送信まで到達していれば、たいてい失敗の記録が残ります）

## まず確かめてほしいこと（順番に）

**1. そもそも、まだ待ち足りないだけではないか**

開始時刻を見ると 07:27〜07:33 とばらついていて、8/13 は 07:33 開始でした。この手の定時実行は数分〜数十分、混雑時には数時間ずれることが珍しくありません。いま何時の時点で「届いていない」と判断されたかによります。8時前後であれば、まだ普通に遅れているだけの可能性が残ります。

**2. 実行の一覧を「失敗も含めて」見る**

貼っていただいた表は状態がすべて「完了」です。もしこの表が成功した実行だけを載せているものなら、**今朝エラーで落ちた実行は、この表には最初から現れません**。実行履歴の画面を開いて、今日の日付で失敗・中断も含めて1件でも記録があるかを見てください。ここで分岐します。

- 今日の記録が1件もある（失敗している）→ 起動はしている。中身のエラーなので、そのログを見れば原因が分かります
- 今日の記録が本当に1件も無い → 起動していない。次へ

**3. 定時実行が止められていないか**

起動自体が無い場合、よくあるのはこれです。

- 定時実行の設定が自動的に無効化されている（GitHub Actions は、リポジトリがしばらく更新されないと定時実行を自動で止めます。画面上部に「このワークフローは無効化されています」といった帯が出ます）
- 設定ファイルを触った、ファイル名やブランチを変えた、といった変更が直前に入っていないか
- サービス側の障害、または実行時間の上限・支払い周りの制限

**4. ためしに手動で1回動かす**

実行履歴の画面から手動実行してみてください。これで動いてメールも届くなら、壊れているのは「仕組み」ではなく「時間になったら起動する部分」だと確定します。逆に手動でも落ちるなら、そのエラーメッセージが答えそのものです。

**5. ついでに迷惑メールフォルダ**

可能性は低い（記録に行が無いので）ですが、確認のコストがゼロなので一応。

## 取りこぼしの心配について

「新着＝前回より後に増えたぶん」という数え方であれば、次に動いたときに前回からの差分をまとめて拾うはずなので、1日飛んでも記事が消えてなくなることは通常ありません。ただしこれは「前回どこまで読んだか」の記録が壊れていない場合の話です。手動実行したときの新着件数が、いつもの1〜5件ではなく極端に多い／0件だった場合は、その記録のほうを疑ってください。

まずは 2 の「今日の記録が1件でもあるか」を見ていただけると、原因が起動側か中身側かで一気に絞れます。その結果を教えていただければ、続きを一緒に見ます。
```

### 返ってきたもの（生） ― 材料A・2回目　`out/aA2.txt`

```
記録を見るかぎり、「メールが送られなかった」のではなく、**今朝ぶんの実行そのものが記録に存在しない**というのが実態です。

## なぜそう言えるか

決め手は **8月14日の行**です。

```
2026-08-14  07:28   完了   13件    0件   なし
```

この日は新着が0件だったのでメールは送られていませんが、**行そのものは残っていて、状態は「完了」**です。
つまり「新着がなかったからメールが来なかった」のであれば、今朝も同じように行が1つ増えて「新着0件・メールなし」と記録されるはずです。行が丸ごと無いということは、メールを送る手前、**実行が始まっていない（または始まったことが記録されていない）**ことを意味します。

もうひとつ、**収集先が壊れた線は薄い**です。取得件数は14日間ずっと11〜15件で安定していて、前日の8/18も13件取れています。収集先が落ちていれば取得件数が減るか状態が「失敗」になるはずで、その予兆がまったくありません。

## 考えられる原因（可能性が高い順）

**① スケジューラが今朝の実行を作らなかった**
いちばんありそうです。開始時刻が07:27〜07:33とばらついていることからも分かるとおり、この種の定時実行は「その時刻ちょうどに必ず走る」保証がありません。混雑時には数時間遅れたり、その回がまるごと飛んだりします。**まだ走っていないだけで、昼前後に遅れて届く**可能性もあります。

**② 定時実行が止められている**
たとえばGitHub Actionsだと、リポジトリに一定期間（60日）更新がないとスケジュール実行が自動で無効化されます。ほかにワークフローが手動で無効化された、権限や課金の状態が変わった、といったケースもここに入ります。この場合、待っていても永久に来ません。

**③ メール送信の認証切れ（今回は可能性低め）**
アプリパスワードの失効などです。ただしこれなら「実行は走ったが送信で失敗」となり、**状態が「失敗」の行が残る**はずなので、行ごと無い今回の症状とは合いません。

**④ 実行もメール送信もされたが、記録の書き込みだけが失敗した**
この場合は**メール自体は届いているはず**なので、迷惑メールフォルダを見れば分かります。

## 確認の順番（上から順に）

1. **受信箱と迷惑メールフォルダ、振り分けフィルタを確認する。** ④の線をまず潰します。届いていればログ側だけの問題です。
2. **実行履歴の一覧で8月19日のエントリを探す。** 「無い」のか「あるが待機中/失敗」なのかで、原因が①②なのか③なのかが分かれます。
3. **手動実行を1回叩く。** 「Run workflow」相当のボタンから手で走らせてください。ここで成功してメールが届けば、設定も認証も生きていて、**スケジューラが今朝の起動を作らなかっただけ**（＝①）と確定します。今日ぶんのまとめもこれで受け取れます。
4. **手動でも失敗するなら、そのログの一番最初のエラー行を見る。** 後ろのほうのエラーは巻き込まれた結果なので、最初の1件が原因です。

## 再発を防ぐなら

今回のように「実行が来ない」タイプの故障は、**何も起きない＝沈黙**という形で表れるので、メールの有無を眺めているだけでは気づけません（「今日は新着ゼロだったのかな」と区別がつかないため）。
「前回の実行から24時間以上あいたら知らせる」という**死活監視を別建てで用意する**のが有効です。実行の成否ではなく「実行があったかどうか」を見るのがポイントです。

まずは迷惑メールの確認と、手動実行の1回。この2つで原因はほぼ絞り込めます。
```

### 返ってきたもの（生） ― 材料B・1回目　`out/aB1.txt`

```
結論から言うと、今朝の処理は「動かなかった」のではありません。**2時間ほど遅れて動き、メール自体は送信されています。**

## 記録のどこを見ればいいか

該当するのは最後の1行です。

```
2026-08-19  09:41   完了   14件    2件   送信 09:43
```

ここから読み取れることが3つあります。

- **状態が「完了」** — 途中でエラーになって止まったわけではありません。失敗なら「完了」にはなりません。
- **取得14件** — 直近14日間は11〜15件で推移しているので、ど真ん中の正常値です。収集先のページも問題なく読めています。
- **新着2件 → 送信 09:43** — 「新着が1件以上なら送る」という条件を満たし、実際に送信まで進んでいます。

つまり、処理の中身はどこも壊れていません。**違っているのは開始時刻だけ**です。予定の07:27に対して09:41なので、2時間14分の遅れです。

## まずやること

メールは09:43に出ているはずなので、**受信箱でその時刻あたりを探してみてください。** 7時半ごろのつもりで見ていると、視界の外にあるかもしれません。

そこに無ければ、次の順で確認します。

1. 迷惑メールフォルダ（プロモーション等のタブがある場合はそちらも）
2. 自分で作った振り分けフィルタが拾っていないか
3. それでも無ければ、送信側が「送信」と記録しているのに届いていないことになるので、そこで初めてメール周りの調査になります

## 「状態＝完了」なのに失敗している理由

ここが一番の落とし穴です。状態が「完了」と出ているのは、**プログラムがエラーで止まらずに最後まで走り切った**という意味であって、**中身が取れたという意味ではありません**。

よくあるのは、収集処理が失敗したときに「エラーを出して止まる」のではなく「**空っぽの結果を返して、そのまま正常終了する**」作りになっているケースです。この作りだと、

収集失敗 → 記事0件 → 新着0件 → 「新着が1件以上のときだけ送る」ルールに従ってメール送信をスキップ → 状態は「完了」

という流れで、**壊れているのに全部が正常に見える**という一番たちの悪い壊れ方をします。今回の記録はまさにこの形です。

## 考えられる原因（可能性の高い順）

取得件数が「減った」ではなく「**全部いっぺんにゼロ**」なのがヒントで、個別の収集先の問題というより、**全部に共通する部分**が疑われます。

1. **収集先ページの構造・URLが変わった**
   収集先が1か所（または共通の作りのページ群）なら、先方のリニューアルで記事の取り出し方が合わなくなり、一夜にして0件になります。この壊れ方をすると「接続はできるが1件も見つからない」＝エラーにならないので、まさに今回の症状になります。

2. **先方に弾かれた（403 / 429 など）**
   アクセス頻度の制限、自動アクセスのブロック、IP単位の遮断など。これも「通信自体は成立している」ので、作りによってはエラー扱いにならず0件になります。

3. **ネットワーク・DNSの一時障害、または先方が落ちていた**
   その時刻だけ繋がらなかった場合。これは翌日ひとりでに直ります。

4. **認証情報（APIキー・トークン等）の期限切れ**
   使っている場合。切れると「認証エラー」ではなく「結果ゼロ」で返す先方もあります。

5. **保存してある状態ファイル（前回どこまで読んだかの記録）が壊れた/消えた**
   ただしこの場合はふつう逆に「全部が新着」になって大量に届くので、今回の症状とは合いません。**可能性は低い**です。

```
「更新が無かっただけ」と「取得そのものが失敗した」を、この記録で見分けられますか。見分けられないなら、見分けるには記録にどの項目を足せばよいかを書いてください。
```

### 返ってきたもの（生） ― 材料A・1回目　`out/hA1.txt`

```
結論から言うと、**見分けられません**。正確には「全部の収集先が失敗した」ときだけは分かりますが、「一部の収集先が失敗した」は、この記録では「更新が無かっただけ」と見分けがつきません。

## なぜ見分けられないのか

**1. 取得件数が合計値だけだから**

取得件数は全収集先の合計です。仮に収集先が5つあって1つが失敗しても、合計が2〜3件減るだけです。この記録の取得件数はもともと11〜15件の間で揺れていて、これは「載っている記事の数が日によって違う」だけでも普通に起きる幅です。つまり**減っていても、失敗のせいなのか、単に古い記事が一覧から落ちただけなのか、区別する材料がありません**。

**2. 「完了」は実行全体が終わったという意味しか持たないから**

状態の欄は毎日「完了」です。ただしこれは処理が最後まで走ったことを示すだけで、途中で1つの収集先が取れずに飛ばされていても、残りが処理できれば「完了」になります。**個々の収集先の成否は、この欄には入っていません。**

**3. 「新着0件 → メールなし」と「取得失敗 → 新着0件 → メールなし」が同じ見た目になるから**

メールは新着が1件以上のときだけ送るので、失敗したときも沈黙します。**受け取る側からは、平和な日と壊れている日が完全に同じ**です。これがいちばん危ないところで、壊れたまま何日も気づかないのはたいていこの形です。

なお 8/14 の「新着0件」は、取得が13件と平常どおりなので**おそらく本当に更新が無かった日**だと推測はできます。ただしこれは前後の日と見比べた推測であって、記録がそう証明しているわけではありません。

優先度の高い順です。

| 足す項目 | これで見分けられるようになること |
|---|---|
| **収集先ごとの行**（名前・成功/失敗・取得件数・新着件数） | 一部失敗。合計にまぎれなくなる |
| **成功数／失敗数**（例: 5件中4成功1失敗）と**失敗の理由**（応答コード・タイムアウト・読み取り失敗） | 失敗の有無と、直し方の見当 |
| **状態を3種類にする**（完了／一部失敗／全失敗） | 一目で異常が分かる。「完了」の一色塗りをやめる |
| **取得0件と取得失敗を別扱いにする** | 「つながったが空だった」と「つながらなかった」は原因が別 |
| **収集先ごとの「最新記事の日付」** | 第3の状態＝*つながるが中身が何週間も止まっている*収集先。これは今の記録では永久に健康に見えます |
| **連続失敗回数／最後に成功した日時** | 「たまたま1回」と「ずっと壊れている」の区別 |
| **メールを送らなかった理由**（新着0件のため／失敗のため送れず） | 沈黙の意味が確定する |

## 最小限でいいなら

全部は重いので、まず2つだけでも効きます。

1. **各行に「成功数／失敗数」を足す**（例: `完了(5/5)`、`一部失敗(4/5)`）
2. **収集先ごとに、そこで見えた最新記事の日付を残す**

この2つがあれば、「取れなかった」と「取れたが新しいものが無かった」と「取れたが中身が止まっている」の3つが分かれます。

## 記録の形の例

```
2026-08-14  07:28  一部失敗(4/5)  取得11件  新着0件  メールなし(新着0)
  ├ A社ブログ    成功  4件  新着0  最新記事 08-11
  ├ B社ニュース  成功  3件  新着0  最新記事 08-13
  ├ C社リリース  成功  2件  新着0  最新記事 07-02  ← 43日更新なし
  ├ D社          成功  2件  新着0  最新記事 08-12
  └ E社          失敗  ―  タイムアウト（3日連続）
```

同じ日でも、これなら「E社は取れていない」「C社は取れているが1か月以上止まっている」「残りは本当に更新が無かっただけ」と、その場で読み分けられます。

あわせて言うと、**行そのものが無い日＝実行されなかった日**も別の異常です。今回は 8/5〜8/18 が1日も欠けずに並んでいるので、その心配はなさそうです。
```

### 返ってきたもの（生） ― 材料A・2回目　`out/hA2.txt`

```
結論から言うと、**この記録では見分けられません**。正確には「全部まとめて失敗した日」だけは運よく分かる可能性がありますが、実際にいちばん起きやすい「一部だけ失敗した日」は絶対に見分けられません。

## なぜ見分けられないのか

### 1. 取得件数が「合計」しか残っていない

収集先が複数あるはずなのに、記録にあるのは全体の合計だけです。たとえば収集先が5つあって、そのうち1つがつながらずに0件だったとしても、他の4つが多めに拾えば合計は12〜13件のまま動きません。**「1つ壊れている日」と「全部正常な日」が、まったく同じ見た目になります。**

実際、取得件数は11〜15件のあいだで毎日ゆれています。8/8 の11件は「たまたま記事が少なかった」のかもしれないし、「1つの収集先が落ちていた」のかもしれない。この記録からはどちらとも言えません。

### 2. 「状態＝完了」が何を意味するのか決まっていない

14日ぶん全部が「完了」です。これは、

- 収集先すべてから正しく取れた
- プログラムが途中で止まらず最後まで走った（取れなかった収集先があっても）

のどちらの意味にもとれます。おそらく後者です。だとすると、**この欄は失敗を表現できていない**ことになります。「14日間ずっと成功していた」のか「失敗しても完了と書かれる作りだった」のかも、記録からは判断できません。

### 3. 新着0件の日が2通りの意味を持つ

8/14 は新着0件です。この日は取得13件が残っているので「記事は読めたが増えていなかった」と言えます。ここは判断できます。

ただし怖いのは逆で、**収集先のページが壊れて古い記事を返し続けている場合**、取得件数は毎日13件のまま、新着は0件のまま、状態は完了のまま。つまり「静かな日が続いている」ようにしか見えません。何日も気づけない壊れ方です。

### 4. 「実行そのものが来なかった日」を表現できない

いまは実行された日だけ行があります。もし記録に無い日があったとき、それは「実行されなかった」のか「実行されたが記録に失敗した」のかが分かりません。今回は8/5〜8/18が抜けなく並んでいるので大丈夫ですが、記録の作り方としては穴です。

## 足すべき項目

優先度の高い順に書きます。**上から2つを足すだけで、目的のほぼすべてが達成できます。**

**① 収集先ごとの1行に分ける（最重要）**

合計をやめて、収集先ごとに「名前・取得件数・新着件数・結果」を並べます。これだけで「どこが失敗したのか」が一目で分かります。

```
2026-08-18 07:30  完了
  A社ブログ    5件  1件  成功
  B社お知らせ   0件  0件  失敗（つながらない）
  C社リリース   8件  1件  成功
```

**② 成功した収集先の数 ／ 予定していた数**

`5/5` のように書きます。細かい行を読まなくても、`4/5` になっていれば「今日はどこか落ちた」とすぐ気づけます。1行で毎日確認するならこれが一番効きます。

**③ 失敗した理由**

「失敗」だけでは打つ手が決まりません。少なくとも次の3つは区別して残してください。

- つながらなかった（相手のサーバーが落ちている・時間切れ）
- 断られた（アクセス拒否。相手側の設定変更が原因のことが多い）
- 読めなかった（ページは取れたが中身の形が変わって解析できない）

直し方がそれぞれ違うので、ここを一緒くたにすると原因調査からやり直しになります。

**④ 収集先ごとの「いちばん新しい記事の日付」**

上の3で書いた「取れてはいるが中身が凍っている」を見つける唯一の手がかりです。ある収集先の最新記事の日付が30日以上前のまま動かなければ、そこは実質止まっています。取得件数は正常なので、これを記録しないと永久に気づけません。

**⑤ 終了時刻（または所要時間）**

いまは開始時刻しかありません。ふだん1分で終わる処理が急に5分かかっていれば、失敗する前ぶれです。

**⑥ 状態欄の値を3つに分ける**

「完了」だけでなく「一部失敗」「失敗」を使えるようにします。②があれば無くても運用できますが、あると人が読みやすくなります。

## 補足：メールの扱いも見直したほうがいいです

いまのルールは「新着1件以上のときだけ送る」なので、**全部の収集先が失敗した日はメールが来ません**。つまり、壊れているときほど静かになります。

「新着0件」と「取得に失敗」を別のものとして扱い、失敗した日は新着が0でも短い通知を送る、という形にしておくと、記録を毎日見に行かなくても異常に気づけます。
```

### 返ってきたもの（生） ― 材料C・1回目　`out/hC1.txt`

```
結論から言うと、**この記録では見分けられません。**

## なぜ見分けられないのか

決定的なのは、記録している「状態」が **完了** の1種類しかなく、しかもそれが「スクリプトが最後まで走ったか」しか表していないことです。取得に失敗して0件を返した実行も、正常に走って0件だった実行も、どちらも同じ「完了・0件」になります。

### 8/19 の行が疑わしい

```
2026-08-19  07:28   完了    0件    0件   なし
```

ここで注目すべきは **新着ではなく取得のほう**です。取得件数の定義は「更新の有無に関わらず、そこに載っている記事の数」なので、

- 更新が無かっただけなら → 取得は 12〜15件のまま、新着だけが 0件（＝8/14 の行がまさにこれ）
- 取得が 0件 → 「収集先のページに記事が1本も載っていない」という、まず起こらない状態

つまり **8/19 は取得失敗の可能性が非常に高い**。ただしそれは定義から逆算した推測であって、記録そのものは何も語っていません。実際には次のどれなのか、この表からは決められません。

- 接続できなかった（ネットワーク・DNS・タイムアウト）
- 接続はできたがエラー応答だった（403・404・500）
- 応答はあったが中身が読めなかった（HTMLの構造が変わった・空のフィードが返った）
- 収集先が本当に一時的に空だった

**打つ手がそれぞれ違う**ので、区別できないと対処のしようがありません。

### もう一つの見えない失敗

収集先が複数ある場合、**一部だけ失敗しても合計値では隠れます**。取得が 13件→12件 と1件減っていても、それが「古い記事が押し出された」のか「収集先の1つが丸ごと落ちた」のか分かりません。日々 11〜15件と揺れているので、この幅に紛れます。

## 記録に足すとよい項目

優先度の高い順です。

### 1. 状態を3つ以上に分ける（最優先）

「完了」をやめて、**成功 / 一部失敗 / 失敗** にします。1件でも取得できなかった収集先があれば「一部失敗」。これだけで 8/19 は一目で失敗と分かります。

### 2. 失敗の理由（エラー内容）

失敗した行に、短くていいので原因を残します。`タイムアウト` `HTTP 403` `解析エラー: 記事が見つからない` など。**エラーの種類が分かれば、待てば直るのか自分で直すのかが判断できます。**

### 3. 収集先ごとの内訳

合計だけでなく、収集先ごとに「取得何件・成否」を残します。1つだけ落ちているのを合計値の揺らぎから救い出せます。

```
日付        収集先        取得   状態
2026-08-19  Aブログ        0件   失敗（タイムアウト）
2026-08-19  Bニュース      0件   失敗（タイムアウト）
```

上のように全部が同じ理由で落ちていれば、収集先ではなく**自分の側のネットワークが原因**だと即座に分かります。これは合計値だけでは絶対に分かりません。

### 4. 所要時間（開始と終了の両方）

いまは開始時刻しかありません。終了時刻を足すと、`0件` が **30秒で即エラーだったのか、5分粘ってタイムアウトしたのか**が分かります。原因の切り分けに効きます。

### 5. 収集先で見えた最新記事の日付

「取得はできるが中身が何か月も止まっている」という**静かな故障**を捕まえるためのものです。取得12件で成功が続いていても、最新記事の日付が45日前のままなら、その収集先は実質的に死んでいます。取得件数と成否だけでは永久に健康に見えます。

### 6. リトライした回数

1回目は失敗して2回目で取れた、という**不安定さの兆候**が残ります。今日は成功していても、リトライ回数が増えていれば近いうちに落ちます。

## まとめの一枚

| 現状の記録 | 足すもの | 何が分かるようになるか |
|---|---|---|
| 状態＝完了のみ | 成功 / 一部失敗 / 失敗 | 0件が異常かどうかが即分かる |
| 理由なし | エラー内容 | 待てば直るか、直しに行くか |
| 合計のみ | 収集先ごとの内訳 | 一部だけ落ちたのを見逃さない |
| 開始時刻のみ | 終了時刻・所要時間 | 即エラーか、タイムアウトか |
| なし | 最新記事の日付 | 取れているのに中身が凍った故障 |
| なし | リトライ回数 | 壊れる前の兆候 |

いちどに全部は要りません。**1 と 2 だけでも 8/19 の判定はつきます**。3 まで入れると原因の切り分けまで自動で終わるようになります。
```

### 返ってきたもの（生） ― 材料C・2回目　`out/hC2.txt`

```
結論から言うと、**半分だけ見分けられます**。両極端はほぼ判別できますが、いちばん危ない「静かに壊れている」状態は、この記録では見分けられません。

## 見分けられるケース

**8/14（取得13件・新着0件）＝「更新が無かっただけ」と言えます。**
収集先のページからは13件ちゃんと読めていて、そのうち前回より後のものが0件だった、という意味なので、取得は成功しています。メールが来なかったのも正常です。

これは「取得件数」という欄を持っているおかげです。新着件数しか記録していなければ、この日は判定不能でした。

## 見分けられないケース

**8/19（取得0件・新着0件）が問題です。**
11〜15件で安定していたものが突然0件になっているので、まず取得失敗を疑うべき日ですが、**記録の上では「完了」で、8/14 と同じ「メールなし」**です。そして次の3つを区別できません。

- 収集先に繋がらなかった（タイムアウト・403 など）
- 繋がったが、ページの作りが変わって1件も抜き出せなかった
- 本当にページが空だった

さらに、次の2つは**もっと見分けられません**。

**① 一部の収集先だけ落ちた場合。** 合計しか記録していないので、取得件数が15→11 に減ったのが「記事が減った」のか「収集先が1つ死んだ」のか分かりません。この記録は普段から 11〜15 で揺れているので、**失敗がその揺れに紛れて完全に隠れます。** 8/19 のような全滅は気づけても、部分的な失敗は永久に気づけません。

**② 中身が凍っている場合。** 収集先が更新を止めて古い記事を返し続けると、取得件数は13件のまま正常に見え、新着だけが0件で並びます。これは「更新が無かった」と見た目が完全に同じですが、実際には数か月前から死んでいる、ということが起こります。

**加えて、状態欄が「完了」しか出していないのも危険です。** 例外を握りつぶして空の結果を返しても「完了」になるなら、状態欄は何も保証していません。

## 足すべき項目

| 足す欄 | 何が分かるようになるか |
|---|---|
| **収集先ごとの行**（合計だけにしない） | 一部失敗が見える。これが最優先 |
| **成功した収集先数 / 全数**（例 12/13） | 部分失敗を1目盛りで検知できる |
| **失敗の種別**（接続不可／タイムアウト／403／抽出0件） | 「経路の問題」と「先方の作りが変わった」を打ち分けられる |
| **状態を3値に**（完了／一部失敗／失敗） | 「完了」の意味が保証される |
| **各収集先で見えた最新記事の日付** | 凍った収集先が炙り出せる（例：30日以上動きなしで警告） |
| **前回の取得件数**（または差分） | 15→11 のような不自然な落ち込みに気づける |
| **所要時間・再試行回数** | 開始が 07:27〜07:33 でばらつく理由が分かる |
| **メールを送らなかった理由** | 「新着0件のため」と「エラーのため」を分けて残す |

## いちばん効く一手

欄を増やす前に、**設計を1つ変えるほうが効きます。**

**「1件も取れなかった」ときは、成功として記録せずにエラーにする。** いまは取得0件が新着0件と同じ扱い（メールなし）になっていて、壊れるほど静かになる構造です。逆に、取得0件のときこそ通知が飛ぶようにしておけば、8/19 は当日の朝に気づけました。

その上で、記録に足す最小セットは **「収集先ごとの成否」と「失敗の種別」の2つ**です。この2つだけで、上に挙げた見分けられないケースのほとんどが解消します。
```
