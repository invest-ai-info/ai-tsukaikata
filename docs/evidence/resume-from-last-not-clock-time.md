# 試した証拠 — resume-from-last-not-clock-time

記事に載せた指示文すべてについて、この形式で残す。返ってきたものは生のまま。
判定は Python（集合演算で重複件数・取りこぼし件数を数える）。仕込み（前回処理済み14件・
新着10件の境目）自体は `gen.py` で機械的に生成し、走らせる前に「正しい対象10件・
処理済み14件・7時より前後の内訳が仕込みどおりであること」を assert で確かめてある
（★24＝真値を作るコードも計測器）。

⚠️ 実測に使ったAIは、このセッション内の新規サブエージェント（Agentツール `claude`）。
事前知識ゼロとは言い切れない（★20）ため、「素のAIはこう返す」という一般化はしない。
機械照合できる結果（ID・件数）だけを記事の根拠にしている。

⚠️ 記事の指示文中の「（ここに受付ログ24件を貼る）」は、実際に送った際はこの位置に
下の教材のログをそのまま展開し、1つのメッセージとして送信した（プレースホルダの
文字列そのものを送ったのではない）。github-actions-daily-cron.md の「○○を書き換えて
ください」と同じ、コピー用テンプレートとしての置き方。

## この記事から出た教訓（`content/_lessons.md` へ）

1. 「時刻を基準」にする指示は、同じ文面・同じ材料で新規の会話に3回通しても、
   選ぶ範囲そのものが割れることがある（21件・18件・4件）。「前回処理済みの位置」を
   基準にする指示は、遅延の事実を伝える・伝えないに関わらず3回とも一致した。
2. 実行が遅れた事実をAIに伝えても、指示文が時刻基準である限り対象範囲は変わらない。
   ただし答えの**安定性**（3回とも同じ答えになるか）だけは上がった。安定＝正解ではない。
3. 「〜より前」で上限を切る時刻基準は割れたが、「〜以降」で下限を1つに固定する
   絶対時刻の指定（初回起動）は2回とも安定して正解した。振れが出たのは
   「今のこの瞬間までの範囲をAIに読み取らせたとき」であって、「時刻を使うこと」自体ではない。
