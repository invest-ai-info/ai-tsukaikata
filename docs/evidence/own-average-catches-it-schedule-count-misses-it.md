`### 自動化・ループ優先` 節の未処理先頭「自分の実行ログそのものを見張らせると、起動が途絶えたことに気づけるか」
（2026-10-11補充）に対する実測。CLAUDE.md「schedule は定刻に来ない」節の実話（1日24回のつもりが実際は5〜7回・
GitHubが実行自体を作っていない）が起点。`auto-health-check`（監視対象の中身の更新停止）・
`resume-from-last-not-clock-time`（遅延後の取りこぼし防止）はどちらも**監視対象**の話で、
**監視する側（自分の実行自体）**の頻度低下を扱った記事は既存に無いことをgrep実測で確認済み
（キュー `_recipe_queue.md` 1030-1035行の根拠欄）。

実測日 2026-10-13。実行方法は前々夜・前夜の担当と同じ＝`Agent`ツール（`general-purpose`／`model: sonnet`）で、
共有コンテキストの無い新規サブエージェントを毎回1回だけ呼び出した（★91＝材料を作った本人〈このセッション〉が
答えも書くと比較が成立しないため、サブエージェントに「ツール不使用・暗算のふつうの無料チャットAI」の役を
演じさせた）。3つの指示文を、それぞれ材料A・材料Bに対して独立した新規呼び出しで**2回ずつ・合計12回**試した
（自動化ものの2回転の決まりに従う）。

真値（日次件数・異常日の集合）はすべて `random.seed(20261013)` の Python で生成し、固定シードで再現可能。

## この記事から出た教訓（`content/_lessons.md` へ）

1. ★257として新規追加＝「予定どおりの実行回数」を基準に自分の実行ログの異常を判定させると、
   元から予定どおりに動かない自動処理（このサイトのトラッカー自身がそう）では、本当に止まっている日も
   ふだんの日も同じ「ほぼ全滅」という答えになり、異常かどうかの情報を運ばなくなる。目安は名目の予定ではなく、
   ログそのものから計算させる。
2. ★143が再発した。「ログに行が無い」ことを、指示文が「0件」と解釈するとは限らない。実際に1回は
   「ログに存在しないので数えない」と明言して、完全停止だけを除外した（`closed-days-vanish-not-zero` と
   同じ壊れ方）。
