## 1. これは何か

「プログラマーではないが、AIに仕事を任せたい人」に向けて、**実際に動いている自動化の手順書**を公開するサイト。

運営者（invest-ai-info）は marketwatch-jp.com で GitHub Actions のワークフローを18本、本番で毎日稼働させている。この実運用そのものが記事の原料であり、他サイトが模倣できない唯一の資産である。

### 目的

収益の第2の柱を作る。marketwatch-jp.com とは読者層も収益経路も分ける。

AIツール分野は YMYL（投資・医療などの高リスク領域）に該当しないため、AdSense 審査は投資サイトより通りやすい。ただし審査は記事が20本を超えてから申請する（不合格理由の第1位は「コンテンツ不足」）。

### 読者

自動化したい非エンジニア。具体的には「Excelマクロは触ったことがある程度、ChatGPTは使っているが自動化まではできていない会社員」。

開発者向けにはしない（日本語圏の母数が小さく、広告もアフィリエイトも弱いため）。AI初心者向け一般記事にもしない（大手メディアが埋め尽くしており差別化できないため）。

| サイト名 | AIの使い方 |

| ホスティング | GitHub Pages（新規リポジトリ） |
| 生成方式 | Python製ミニSSG（Jinja2 + Markdown） |
| 生成HTML | git にコミットしない（Actions から Pages へ直接配信） |
| ローカルパス | `C:\Users\info0\ai-tsukaikata`（OneDrive外。同期による `.git` 破損を避けるため） |
| 初回公開の範囲 | トップ + レシピ記事5本 |

### 採用しなかった案と理由

**Astro などの本格SSG** — 品質は最高だが Node 環境と `node_modules` が増え、ビルドが壊れたときの調査が運営者にとって未経験領域になる。得られる品質差が学習コストに見合わない。

**marketwatch-jp.com の生成方式（Pythonで文字列としてHTMLを直生成）の移植** — あの方式は「毎日データが変わる固定ページ」には最適だが、「記事が積み上がるサイト」には向かない。記事20本前後でテンプレートと本文が絡まり保守が破綻し、後からSSGへ移行する際に全記事の書き直しが必要になる。

**marketwatch-jp.com のサブディレクトリ／サブドメイン** — ドメイン費用はゼロだが、投資サイトにAIツール記事が混ざるとテーマの一貫性が崩れ、両方の専門性評価が下がる。読者層も収益経路も別なので分ける。

**ドメイン名にキーワードを詰め込む方針** — Google は2012年の EMD アップデート以降、ドメイン名のキーワードをほぼ評価しない。新規サイトの流入は記事単位の長尾検索から来るため、ドメインは覚えやすさで選ぶ。

## 3. コンテンツ設計

### カテゴリ（初回公開時点）

| カテゴリ | 役割 | 出どころ |
|---|---|---|
| レシピ (`recipes`) | 主軸。動く自動化の手順 | 運営者の実運用 |
| ツール (`tools`) | 補助。使い方・比較 | 実際に使っているツールのみ |
| 固定ページ (`pages`) | about / プライバシーポリシー等。一覧には出さない | 手書き |

ニュース (`news`) は第2段階。初回公開には含めない。

### レシピ記事の固定フォーマット

> **改訂（2026-08-02）**: 3番と4番を**コードからプロンプトに変更した**。理由は下記。

全記事この5ブロックで統一する。

1. **これで何ができるか** — 3行 + 完成イメージ
2. **前提** — かかる時間 / 費用 / 必要なもの（**プログラミング不要**を明記）
3. **AIへの頼み方** — そのままコピーできる指示文と、「なぜこの言い方か」
4. **うまくいかないときの言い直し方**
5. **応用・次の一手**

4番がこのサイトの差別化の核である。公式ドキュメントの翻訳記事には書けず、実際に動かしていない人には書けない。運営者の `github-actions-cron-best-practice` スキルにある「cronの混雑回避」「遅延前提の設計」のような知見が、**指示文の形で**ここに入る。

#### なぜコードではなくプロンプトなのか（2026-08-02 の改訂理由）

初版はブロック3を「コピペできるコマンドとコード」としていたが、実際に5本書いてみて**読者定義と矛盾していた**ことが分かった。想定読者は「Excelマクロは触ったことがある程度の会社員」であり、PythonとYAMLが並ぶ記事は読めない。

加えて、**運営者自身がコードを手で書いていない。**AIに頼んで作らせたものが本番で動いている。であれば公開すべき資産は、書いたコードではなく**頼んだ言葉**のほうである。ここは他サイトが模倣しにくく、読者が今日そのまま使える。

**コードを残す基準:** 読者が自分で打つものは残す。AIが書くものは載せない。

- 残す — 読者がターミナルに打つ1行、その実行結果の表示
- 載せない — 関数の中身、設定ファイルの全文、ワークフローのYAML

#### プロンプトの書式

記事中の指示文は生HTMLで書く。Markdownの引用記法（`>`）は使わない。**コピーしたときに原文どおりになる**ことを優先するため。

```html
<div class="prompt">AIに渡す指示文をそのまま書く。
改行はそのまま出る（CSSで white-space: pre-wrap）。</div>
```

### 初回公開の5本

すべて運営者が実際に運用している自動化であり、事実の裏付けがある。

1. **AIの最新情報を自動で集めて、重要なものだけメールで受け取る**（1段目のトラッカーを作った実作業がそのまま原料になる。サイトのテーマとも最も近い）
2. GitHub Actions で「毎日決まった時刻に自動実行」を無料で作る（cronが遅れる・走らない問題の対処込み）
3. YouTube動画を毎晩自動で要約させる
4. サイトやサービスの異常を自動検知して通知する
5. Claude Code に「記憶」を持たせて毎回説明し直さなくする

次に書く候補: 無料でメールリストを作り全ページに自動設置する / 静的サイトを自動ビルドして公開する。

### ディレクトリ構成

```
ai-tsukaikata/
├─ content/
│  ├─ recipes/                 # レシピ記事（Markdown + frontmatter）
│  ├─ tools/                   # ツール記事
│  ├─ pages/                   # about / プライバシーポリシー等
│  └─ _ideas.md                # 記事ネタのメモ置き場（ビルド対象外）
├─ templates/
│  ├─ base.html                # 共通レイアウト
│  ├─ article.html             # 記事ページ
│  ├─ index.html               # トップ
│  └─ list.html                # カテゴリ一覧
├─ static/
│  ├─ style.css
│  └─ images/
├─ src/
│  ├─ build.py                 # 全体をつなぐ。唯一ファイルを書く場所
│  ├─ content.py               # Markdown読み込み → Article
│  ├─ render.py                # Article + テンプレート → HTML文字列
│  ├─ feeds.py                 # RSS / sitemap.xml / robots.txt
│  └─ validate.py              # 公開前チェック
├─ tests/
├─ build/                      # 生成物（.gitignore対象）
├─ .github/workflows/build.yml
├─ requirements.txt
└─ docs/superpowers/specs/     # この設計書
```

### モジュールの責務

ファイルを書くのは `build.py` だけ。それ以外は入力を受けて値を返すだけの純粋な関数なので、ディスクを触らずにテストできる。

| モジュール | 入力 → 出力 | 依存 | 知らないこと |
|---|---|---|---|
| `content.py` | content/のパス → `Article` のリスト | markdown, pyyaml | テンプレート、HTML |
| `render.py` | Article リスト → HTML文字列の辞書 | jinja2 | ファイルシステム |
| `feeds.py` | Article リスト → RSS/sitemap/robots の文字列 | 標準ライブラリのみ | テンプレート |
| `validate.py` | Article リスト → エラーのリスト | 標準ライブラリのみ | 書き込み |
| `build.py` | 上記を呼び `build/` に書き出す | 全部 | — |

### 記事の契約（`Article`）

読み込んだ後は不変（`@dataclass(frozen=True)`）。

```python
@dataclass(frozen=True)
class Article:
    slug: str            # ファイル名から導出（URLになる）
    title: str
    description: str     # メタディスクリプション兼カード文
    category: str        # "recipes" | "tools" | "pages"
    published: date
    updated: date | None
    tags: tuple[str, ...]
    time_required: str | None   # レシピのみ
    cost: str | None            # レシピのみ
    body_html: str              # Markdown変換済み
    source_path: Path
```

frontmatter の例:

```yaml
---
title: GitHub Actionsで毎日決まった時刻に自動実行する
description: 無料のcronスケジュール実行を設定し「走らない・遅れる」問題まで潰す手順。
category: recipes
published: 2026-08-01
tags: [GitHub Actions, 自動化, 無料]
time_required: 30分
cost: 無料
---
```

必須項目は `title` / `description` / `category` / `published`。`recipes` カテゴリではさらに `time_required` / `cost` を必須とする。

### URL設計

```
/                             トップ
/recipes/                     レシピ一覧
/recipes/<slug>/              レシピ記事
/tools/                       ツール一覧
/tools/<slug>/                ツール記事
/<slug>/                      固定ページ（about, privacy 等）
/feed.xml  /sitemap.xml  /robots.txt
```

末尾スラッシュ形式（`build/recipes/<slug>/index.html`）で出力する。GitHub Pages でそのまま動き、後からURL構造を変えなくて済むため。

## 5. 記事ができるまでのデータフロー

```
① ネタ発生   運営者が日々やっている作業（新ワークフロー追加、詰まって解決したこと）
② ネタ捕捉   content/_ideas.md に1行メモ、または対話で「この前の○○を記事にして」
③ 下書き生成 Claude が"実物"（ワークフローYAML・スクリプト・コミット履歴）を読んで
             レシピ形式の Markdown を content/recipes/ に書く
④ 目視確認   運営者が読む ← 事実誤認・言い過ぎ・機密の最終ゲート
⑤ 公開       git push → Actions がテスト→ビルド→Pages配信
```

③で**実物を読む**ことが必須である。記憶や一般論から書くと「実際に動かしていない記事」になり、このサイト唯一の武器を失う。

④は人間による確認を必ず挟む。完全自動公開はしない。

## 6. 検証と安全装置（`validate.py`）

### 最大のリスク: 機密漏れ

marketwatch-jp.com 側には公開してはいけないものがある（APIキー、MailerLite の ID、非公開の検証ノート、ローカル絶対パス）。記事化のたびに人間の注意力に頼る運用は必ず事故を起こすため、コードで止める。

以下を検出した場合、ビルドを失敗させる。

| 検査 | 内容 |
|---|---|
| トークン形式 | `ghp_` / `github_pat_` / `sk-ant-` / `AKIA` などのプレフィックス |
| 認証情報 | `.env` 形式の行、`password=` / `api_key=` などの代入 |
| メールアドレス | 記事本文中の生のメールアドレス |
| ローカル絶対パス | `C:\Users\` を含む文字列 |
| frontmatter | 必須項目の欠け、日付形式、未知のカテゴリ |
| slug | 重複 |
| 内部リンク | 本文中の内部リンクの参照先slugが実在するか（Articleリスト内で照合） |
| 広告表記 | アフィリエイトリンク（`a8.net` 等）を含む記事に「広告」または「PR」の表記があるか |

最後の広告表記チェックは景表法のステマ規制対応であり、法的に必須である。人間の記憶に頼らずコードで強制する。

なお本設計書は法的助言ではない。広告・表示に関する最終判断は専門家の確認を経ること。

### エラー処理の方針

ビルドは「全部通る or 何も出さない」。壊れた記事が1本でもあれば全体を止める。公開されるものが常に検証済みである状態を保つため。

ただし `validate.py` は最初のエラーで止めず、**全エラーを収集して一覧で報告してから**失敗する。1個直して再実行という往復を避けるため。

## 7. CI/CD（`.github/workflows/build.yml`）

```
トリガー: push（content/ templates/ static/ src/ の変更時）+ workflow_dispatch
ステップ: checkout → setup-python → pip install -r requirements.txt
        → pytest → python src/build.py
        → actions/upload-pages-artifact → actions/deploy-pages
```

- `workflow_dispatch` は必ず付ける。手動実行できないワークフローは詰まったときに手が出せなくなる。
- **テストが落ちたらデプロイしない。** 壊れたものは公開に到達しない。
- cron は初回公開時点では不要。第2段階のニュース自動収集で追加する。
- 生成HTMLは `.gitignore` に入れ、リポジトリにはコミットしない。git に入るのは Markdown・テンプレート・コードのみ。差分が読め、コンフリクトせず、上書き事故が起きない。

## 9. スコープ外（第2段階以降）

初回公開には含めない。ただし後から足せる形にしておく。

- **更新情報の公開ページ化** — トラッカー（1段目）が集めた `Update` を `Article` と同じ形に落として公開ページにする。まず自分用に運用してソースとノイズを調整してから着手する。設計は[トラッカー設計書](2026-08-01-ai-update-tracker-design.md)を参照。
- **使い分けマップ（3段目）** — どのAIが何が得意かの比較。トラッカーが数週間データを貯め、運営者が実際に使い比べた根拠ができてから着手する。受け売りの比較表には価値がないため、それ以前には作らない。鮮度が命なので「最終確認日」を必須項目にする。
- **AdSense** — 記事20本を超えてから申請する。
- **アフィリエイト** — 記事が貯まってから。設置時は `validate.py` の広告表記チェックが効く。
- **メールリスト** — 収益化フェーズで検討。
- **タグページ・検索・関連記事** — 記事数が増えてから。

## 11. リスクと対応

| リスク | 対応 |
|---|---|
| 機密情報の漏れ | `validate.py` で検出しビルド失敗（§6）。加えて④の目視確認 |
| 記事が続かない | 半自動生成で1本あたりの手間を数分に抑える。ネタは実運用から自然に湧く |
| 「実際に動かしていない記事」の混入 | 下書き生成時に実物を読むことを必須とする（§5③）。完全自動公開はしない |
| marketwatch側への注意分散 | 初回は最小構成（5本）に絞る。ニュース自動収集は第2段階へ後倒し |
| ステマ規制違反 | 広告表記チェックをコードで強制（§6） |
| OneDrive同期による `.git` 破損 | リポジトリをOneDrive外（`C:\Users\info0\ai-tsukaikata`）に置く |
| ~~ドメインが取得できなかった場合~~ | 解消済み（`ai-tsukaikata.com` を取得） |
