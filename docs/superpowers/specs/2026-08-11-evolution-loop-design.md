# 進化ループ — 記事を書くたびにサイトが上手くなる仕組み（設計書）

日付: 2026-08-11 ／ 状態: **オーナー承認済み**（同日・チャットで各節提示のうえ承認）

## きっかけ（オーナー指示・2026-08-11）

「いつも同じようなペースで記事を作ると、質が低くなり、読者も読む気がなくなる。
常に進化させる仕組みを作ってほしい。見やすく・わかりやすく・便利であることが大事。
記事を書くたびに、内容を進化させるような仕組みを設計してほしい」

- 2026-08-04 指示「見やすい・わかりやすい・便利を常に自立進化させていってほしい」の本体設計
- 追加指示（同日）:「記事のストックはどんどん作って消化していく」→ **キューを枯らさない運用**を含める
- 優先順位はオーナー回答＝**3つとも太く**（中身の質／読者に見える改善／題材の当たり）。
  土台は「中身の質」（他の2つの燃料源になるため）

## 0. 前提の実測（設計の根拠）

| 実測 | 帰結 |
|---|---|
| 教訓は**毎晩1〜4件、自然に発生している**（8/8=3件・8/9=1件・8/10=4件） | 作るのは「進化を発生させる装置」ではなく**「取りこぼさない装置」** |
| 教訓の置き場が散在（キューの題材別メモ・handoff）で、翌晩の担当が読む保証も、コードへ昇格する道も無い | 置き場を1つにし、昇格の道を定める |
| `validate.py` のゲートは「悪い記事を止める」だけで、上へ押す力は無い | ゲート（下げ止め）と進化（記憶と昇格）は別の仕組み |
| 読者信号が現在ゼロ（Search Console 未登録） | 「読まれる方向」の進化は登録後に実データで回す |
| 1本あたり実測12分（3晩の実行履歴） | 3本/晩でも時間の制約は無い。証拠書き出しの追加も吸収できる |
| キュー未処理13件・3本/晩 | **4晩で枯れる**。補充は「いつか」ではなく今週の問題 |

## 1. 決定経緯（検討した3案）

| 案 | 中身 | 判定 |
|---|---|---|
| **A: 3つの輪**（台帳→コード→データ） | 教訓をファイルに蓄積→週次でコードへ昇格→読者データで方向修正 | ✅ **採用。**家の流儀そのもの（ルールはコードへ・点数無し・番人分離） |
| B: プロンプト週次改訂 | 教訓をルーティンのプロンプトへ直接足す | ❌ 「プロンプトは凍る・2か所問題」（2026-08-11 に実害を確定させたばかり）への逆走 |
| C: LLM採点→自動リライト | 記事を採点し、基準未満なら書き直させる | ❌ B2スコアの前例（横一線=無益）。自己採点は「試したか」を原理的に検出できない。**その場の磨きで翌晩に何も残らない＝進化ではない** |

🔑 **「良い記事を1本作る仕組み」と「記事を作るたびに上手くなる仕組み」は別物。**
前者はゲート（もうある）。後者は**記憶と昇格**（無かった）。この設計が作るのは後者。

## 2. 全体像

```
毎晩の「試して分かったこと」
   ↓ 書き残す                （輪1: 台帳・証拠 — 毎晩）
まだコードになっていない教訓のファイル
   ↓ 2回出たら昇格           （輪2: 人間+Claude — 週1・月曜）
validate.py / 記事の型 / 図の部品   ← ここに入ると全記事に恒久適用
   ↑ 方向を決める             （輪3: 読者データ — 月1 or データ到着）
Search Console・サジェスト再実行・キュー補充
```

**夜=中身、週=型、月=方向。**記事ごとに型まで変えない——型の一貫性そのものが
読者のナビゲーション（見やすさ）なので、型は週に1度・1つずつしか動かさない。

## 3. 輪1 — 継承（毎晩・記事ごと）

### 新ファイル2種

**`content/_lessons.md`（書き方の台帳）**
- **まだコードになっていない教訓だけ**を置く短いファイル
- 1件の形式＝「日付／出た記事／事実（証拠ファイルへのリンク）／次からどう書くか」
- 昇格したら「昇格済み」欄へ移す。**台帳は待合室であって住所録ではない**——
  生きている教訓が15件を超えたら週次で整理する（長い台帳は読まれなくなって死ぬ）
- 夜の担当は**追記のみ**（既存の教訓と「昇格済み」欄を書き換えない）

**`docs/evidence/<slug>.md`（試した証拠）**
- 記事に載せる指示文ごとに: 入力（架空データ）／送った指示文（**記事と同一文字列**）／
  返ってきたもの（生・要約しない）／判定＝採用・直した・落とした
- ⚠️ **`content/` の中に置かない。**ビルド除外は**ファイル名**の `_` 判定
  （`content.py` の `path.name.startswith("_")`）なので、`content/evidence/` は記事として拾われる
- 対象はレシピのみ（深掘りは `check_numbers.py` の生テキスト照合が既にある）

### 担当の義務（キューの「担当が守ること」に2条追加）

1. 書く前に `content/_lessons.md` を全部読んで適用する
2. 試した記録を `docs/evidence/<slug>.md` に残す。学んだことがあれば台帳に足す

- ⚠️ **教訓の追記はノルマにしない**（本数ノルマと同じ罠。実測で毎晩1〜4件自然に出ている。
  義務は「読む・証拠を残す」の2つだけで、「学びを申告する」は義務にしない）
- 📌 **プロンプトの再貼り替えは不要。**「キューの各条が指示書」の形（2026-08-11 の修正）なので、
  キューに足せば届く

## 4. 輪2 — 昇格（週1・月曜30分・人間+Claude）

月曜は freshness メール（9:40 JST）が来る日なので、そこに相乗りする。メニューは固定4つ:

1. **昇格判定** — 台帳で2回出た教訓／全題材に効く教訓を `validate.py`・記事の型・
   `make_figures.py` の部品へ昇格する。**教訓の一般化はここでやる**（夜の担当は題材固有の
   まま書いてよい。「翻訳の回数は合わない」＋「表の平均はずれる」→「AIの集計値は照合可能な
   形で出させる」に束ねるのは判断の仕事）。
   ⚠️ 新しい検査は**本番データで1回流して鳴り方を見てから**有効化（偽陽性3種の教訓）
2. **拾い読み1種** — マーカー／導入文／図をローテで通し読み（機械にできない検査）
3. **読者に見える改善を1件だけ** — バックログから1つ適用し、翌週に効果を見る。
   種: 指示文まとめコピー・長い記事の目次・間違い報告リンク（公開面なので実施前に
   オーナー判断）・図の新しい形・関連記事の提示
4. **キューの残量確認** — 未処理が**6件（=2晩ぶん）を切っていたら補充を最優先**にする

**番人の分離:** 夜の担当は `validate.py`・ルーティンのプロンプト・記事の型・台帳の
「昇格済み」欄を**触らない**。昇格は人間セッションのみ。

## 5. 輪3 — 方向（月1、またはデータ到着ごと）

- ⭐ **Search Console**（運営者5分・未登録）— 実クエリと既存記事・キューの突合。
  「読まれる記事を書く」方向の進化は、これが来て初めて実データで回る
- **サジェスト総当たりの再実行** — 種を増やして流す（手順コードは
  `docs/superpowers/notes/2026-08-10-demand-research.md` に保存済み・再実行可能）。
  キュー未処理6件未満が引き金。3本/晩だと実質毎週になるので、輪2のメニュー4と一体で回る
- **リンクの張り直し** — 新記事のテーマを古い記事が触れていたら、**古い記事→新記事**の
  リンクを足す。リンク網が「新→旧」にしか張られない構造的偏りを直し、古い記事も生き返る

## 6. v1.5 — 証拠の機械照合（数晩後）

`validate.py` に決定的検査を追加する（LLM不使用・ぶれない）:

- レシピの `<div class="prompt">` の各文字列が、対応する `docs/evidence/<slug>.md` に
  **完全一致**で存在すること
- その指示文に対応する「返ってきたもの」が空でないこと

**「試したか」が初めて検査可能になる。**捏造は完全には防げないが、架空の入出力を
全部でっち上げるほうが実際に試すより高くつくので、動機が逆転する。
⚠️ 2〜3晩ぶんの実物の証拠ファイルで**較正してから**有効化（既存記事は対象外に始める。
`checked` と同じ理屈＝全記事必須にすると既存が全部落ちる）。

## 7. やらないこと

- **点数化**（B2信頼度スコアの前例: HIGH/MID/LOW が 42.8/41.1/43.2% で横一線＝無益）
- **記事ごとの型変更**（型は週に1度だけ。一貫性は読者のナビゲーション）
- **教訓・本数のノルマ化**（ノルマは「実際に試す」を最初に削らせる）
- **プロンプトへの知識書き込み**（プロンプトは凍る。手順だけを書き、変わりうるものはリポジトリに置く）
- **夜間のゲート・型・台帳既存部の変更**（番人の分離）
- **台帳の無限成長**（待合室であって住所録ではない）
