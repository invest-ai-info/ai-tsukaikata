# ライター作業のトークン食の設計 — 会話の長さの2乗を断つ

作成: 2026-08-27 22:05 JST（オーナーの依頼「記事を書く手順をクオリティ落とさずにトークンを節約した方法で設計」）
状態: **設計承認済み（2026-08-27 オーナー承認・案1）**。実装はこれから

対象: **手動ライター作業**（earn場面キューを1本ずつ高品質に仕上げる作業。次＝3本目「時給の推移を週ごとに並べる」）。
自動ルーティン側は§7（第2段＝効果実測後に移植）。

## 0. 診断 — トークンはどこに消えているか

ファイル在庫は 2026-08-20 の回転で済んでいる（▲47%・`2026-08-20-token-diet-design.md`）。
残る浪費源は**会話側**：

- コスト式（2026-08-21 実測・誤差5%以内）＝ **ターン数 × 平均文脈 × 0.1**。文脈はターンごとに
  積み上がるので、**会話の長さの2乗**でコストが増える。実測で古い会話と新しい会話に**1ターン最大4.9倍の差**
- 2本目（job-ai-policy-check）は実測39回＋独立レビュー2回＋修正＋裏取りを**1つの長い会話**で実施＝
  39回の実測結果・レビュー指摘・修正のやり取りが全部文脈に積もり、以降の全ターンがそれを払い続けた
- 内訳の実測（8/21週）：読み直し50%・新規読み込み41%・出力9%＝**払っているのは仕事の中身ではなく会話の長さ**

## 1. 触らないもの（品質の本体だから）— 先に宣言する

| 触らない | 理由 |
|---|---|
| **実測の回数と独立性**（1実行=1フレッシュ文脈・真値を渡さない） | 差別化の源泉。★91で確立した運用そのまま |
| **証拠の全文主義**（`docs/evidence/<slug>.md`・指示文は同一文字列で全文） | `_evidence_errors()` の照合規約は不変。畳まない |
| **独立レビュー**（材料だけ渡す・指摘リスト方式・指摘が尽きるまで） | 1本目11回/2本目2回の実績。回数は品質が決める |
| **判定コードの生テキスト再実行での裏取り** | 2本目で判定コードのバグ2件を捕まえた層。むしろ§4で強化する |
| **機械検査**（pytest / src.build / check_numbers.py） | 現行どおり全部通す |

削るのは「**同じ文脈を何度も読み直すこと**」だけ。

## 2. 会話①＝企画＋実測

1. **読むもの**: SOP（§5）＋キューの**該当項目だけ**。`_recipe_queue.md`（2,082行）は Grep で題名を
   探し、該当節を offset/limit で部分読み。**全読み禁止**
2. **企画**: 記事構成と実測計画（何を・何回・どの条件で）を決める
3. **判定スクリプトを先に書く**: `docs/evidence/_raw/<slug>/judge.py`。判定基準（正規表現・数え方）を
   **実測前に**コード化する。🔑 2本目は判定コードのバグ（括弧入り見出しの取りこぼし・活用形漏れ）を
   独立レビュー2回目まで発見できなかった。先にコードにすれば、実測の1回目から同じ物差しで測れる
4. **実測は並列サブエージェント**: 1メッセージに複数の Agent 呼び出しを並べる（各呼び出し＝独立文脈。
   39回を39ターンでなく数ターンにする）。各サブエージェントは:
   - 渡されるのは**依頼＋材料だけ**（仕込みの答え・真値は渡さない＝★91の運用）
   - 生の全文を `docs/evidence/_raw/<slug>/runNN.md` に**自分で書く**
   - 親には**条件と判定用の数行だけ**返す（全文を返さない＝親の文脈が太らない）
5. **集計は judge.py を raw 全体に流す**（手集計しない）。出力の集計表を土台に証拠ファイル
   `docs/evidence/<slug>.md` を組み立てる
6. **終わり方**: キュー該当項目に「実測済み・要点・rawパス」を数行注記 → commit・pull --rebase・push →
   `_writer_log.md` に実測行を記録 → 会話終了。オーナーが新しい会話で②を始める

## 3. 会話②＝執筆〜公開

1. **読むもの**: SOP＋キュー該当項目（①の注記込み）＋証拠ファイル。**raw は読まない**
   （判定はスクリプト済み。疑義が出た run だけ開く）
2. 執筆（記事の型は現行どおり: 5ブロック・マーカー上限・数値比較記事は図2枚以上・座標は計算）
3. 機械検査: `pytest` / `python -m src.build` / `tools/check_numbers.py`
4. **独立レビュー**: 現行どおり。材料（記事＋証拠＋judge.py の集計）だけ渡し・指摘リストだけ返させる・
   指摘が尽きるまで繰り返す
5. **修正の裏取り**: 数字を直すときは judge.py を raw に再実行してから（手で数字を書き換えない）
6. 公開・キュー「→保管」注記・`_writer_log.md`（実測行は回ごと1行）・commit・pull --rebase・push
7. **成り行き条項**: 文脈警告🟠（300k）を超えて作業が続くなら、レビュー境界で引き継ぎ注記を書いて
   もう1回切ってよい。判断はその場の Claude（警告の物差しは `~/.claude/context-budget.ps1`＝150k🟡/300k🟠/500k🔴）

## 4. raw ファイルと判定スクリプトの規約

- `docs/evidence/_raw/<slug>/runNN.md` ＝ **1実行1ファイル・逐語全文**。冒頭に条件（版・材料・
  実行方法・日時）を数行のヘッダで書く
- `docs/evidence/_raw/<slug>/judge.py` ＝ 記事ごとの使い捨てだが**リポジトリに残す**
  （いつでも再実行で裏取りできる＝再現可能性が上がる）
- 🚨 **中略した抜粋で判定を出すことを禁止。判定は必ず raw へ**（8/27 の実測：中略が判定行を落として
  「2/3」が実際は「3/3」だった。この教訓の恒久化）
- `docs/evidence/` はビルド対象外（`content/` の外）＝サイトに出ない。`build.yml` の `paths:` にも
  含まれないので、raw の push で再デプロイは走らない
- 証拠ファイル本体（`docs/evidence/<slug>.md`）の規約は**一切変更なし**

## 5. SOP ファイル — `content/_writer_sop.md`

- 80行前後・チェックリスト形式。①②の手順＋§1の不触宣言＋禁止3点
  （**全読み禁止・手集計禁止・真値を渡さない**）
- `_` 始まり＝ビルド対象外。**静的ファイル**（増え続けるログではない）ので `file_budgets()` の
  行数予算は付けない
- SESSION_HANDOFF には「ライター作業＝`content/_writer_sop.md` 参照」の1行だけ置く
  （手順の複製を書かない＝複製は必ず古くなって嘘をつく）

## 6. 効果測定

- `python ~/.claude/token-report.py` で **2本目（8/27 のセッション）と3本目を比較。目標▲50%**
- 品質の対照（下がっていないことの確認）: 独立レビューの指摘件数・機械検査 green・オーナー通読
- ⚠️ 実測回数が記事ごとに違うので、1本あたり総量だけでなく「実測1回あたり」も併記する

## 7. ルーティンへの適用（第2段・効果実測後）

| 部品 | 適用 | 理由 |
|---|---|---|
| 並列実測＋raw保存＋要約だけ返す | ⭕ | ★91の「Agentツール・材料だけ渡す」が土台。スケジュール起動でも動く（8/24実証） |
| 判定スクリプト前倒し | ⭕ 品質面でも有効 | 裏取りの機械化。ルーティン向き |
| 2会話分割 | ✖ 不要 | ルーティンは毎晩フレッシュな1セッション＝会話長が有界。`scheduled_trigger` からは `create_session` も使えない |

- ⚠️ クラウド側の消費は**このPCのログに残らない**＝効果測定不能。品質面の利点（raw＋judge.py）は
  測定不能でも有効
- ⚠️ ルーティンのプロンプトは**repoに無い**（クラウド設定側）。移植はプロンプト実物を読んでからの改修
- 🔑 段階方式（前回ダイエットと同じ）: 3本目で効果を実測 → 効いたことを確認 → ルーティンへ移植
