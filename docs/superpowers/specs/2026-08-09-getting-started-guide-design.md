# 設計: 始め方の指南書（/start/）

作成: 2026-08-09。オーナーとのブレインストーミングで決定。

きっかけ＝オーナー指示「ページのトップに、各ツールの始め方の説明を載せてほしい。インストール方法、
必要なもの、PCのスペックとか、初心者でもわかるように」。

## 決まったこと（経緯）

| 論点 | 決定 |
|---|---|
| 対象ツール | **ブラウザ版3つ（ChatGPT / Claude / Gemini）＋ Claude Code** |
| 鮮度 | **具体に書く＋確認日を出す＋機械で見張る**（構造だけ書いて公式に逃がす案は却下＝初心者が知りたい「で、何を押すの」が消える） |
| 構成 | **1枚もの `/start/`**。トップはヒーロー直下に導線。ツール別4ページ案は、反応を見てから分ける |
| OS | **Windows 中心＋Mac は公式リンク**。この環境で確かめられるのが Windows だけなので、確かめていない手順を書かない |
| 検査の置き場所 | **書き忘れ＝ビルドで止める／古さとリンク切れ＝週次で知らせる**（下記①の落とし穴） |
| スペックの扱い | **必要最低限を具体的に示す**（オーナー指摘で方針転換。下記④） |

## ① なぜ「古さ」でビルドを止めないのか（この設計の要）

`build.py` は「全部通る or 何も出さない」。**確認日が古いことでビルドを止めると、毎晩21:00の
レシピ担当が記事を push した夜に、指南書の日付が理由でその記事が公開されなくなる。**
担当は成功したと記録し、サイトには出ない——このサイトが一番警戒している「静かな欠落」になる。

性質で分ける:

| 何が起きたか | いつ起きるか | どうする |
|---|---|---|
| `checked:` が壊れている・未来日付 | 書いた本人がその場にいる | **ビルドで止める** |
| `checked:` の書き忘れ | 書いた本人がその場にいる | **止めない。週次の一覧に出す**（理由は⑥） |
| 確認日が古くなった | 時間が経てば勝手に起きる | **週次で知らせる。止めない** |
| 外部リンクが切れた | 相手の都合で勝手に起きる | **週次で知らせる。止めない** |

## ② 置き場所

`content/pages/start.md` → `/start/`（`content.py:49` で `pages` は `/{slug}/`）。
category は `pages` なのでレシピ用の密度ゲート（指示文6個・図1枚・本文1800字）は当たらない。
ただし**図は2枚入れる**（オーナー指示「図は既定で入れる」に従う。ゲートが無いから省くのではない）。

導線は2か所:

- `templates/index.html` の**ヒーロー直下・AIアップデートより上**に導線セクション
- ヘッダーの nav

## ③ ページの構成

節の順番が設計の本体。**初心者の最初の不安は「自分のPCで動くのか」なので、そこを最初に潰す。**

| # | 節 | h2 class | 中身 |
|---|---|---|---|
| 1 | 自分のPCで動くかを、先に確かめる | `.need` | スペックの調べ方 → 最低要件 → 足りないときの逃げ道（図①） |
| 2 | どれから始めるか | `.what` | ブラウザ3つ＝今日5分。Claude Code＝レシピを動かすため。迷ったときの選び方 |
| 3 | ブラウザで使う3つ | `.ask` | ChatGPT / Claude / Gemini。入口・必要なもの・無料でできること・確認日 |
| 4 | Claude Code を入れる（Windows） | `.ask` | 必要なもの → 手順 → 動いたかの確かめ方。Mac は公式へ（図②） |
| 5 | つまずいたときの直し方 | `.fix` | よくある詰まり |
| 6 | 次の一手 | `.next` | `start` の場面の記事へ内部リンク |

⚠️ `validate.py` は「h2に1つでもclassが付いていれば全部に必要」なので、**6節すべてに付ける**。
class は5種しかないので `.ask` を2回使う（節3と節4はどちらも「頼み方・手順」なので意味も合う）。
⚠️ **節1が `.need`（📋 準備）で節2が `.what`（🎯 これで何ができるか）と、レシピの並びとは逆になる。**
これは意図的で、この記事だけは「自分に使えるのか」を先に答える必要があるため。

## ④ 「PCのスペック」の書き方

⚠️ **初稿の方針「スペックは関係ない」はオーナー指摘で撤回した。**
理由＝50代・60代の人や、PCを買えない中高生は、**スペックの足りない古いPCを使っている可能性がある**。
そういう人ほど「自分のPCで大丈夫か」を知りたくてこのページに来る。「関係ない」は、
新しめのPCを持っている人だけに成り立つ答えだった。

5段構成にする。

**1. まず、自分のPCが何なのかを調べる**
「メモリ8GB必要です」は、自分のPCのメモリを知らない人には何も伝えない。
Windows での確認手順（設定 → システム → バージョン情報）から始める。**この環境で実際に踏んで確かめる。**

**2. 実質の足切り線は「ブラウザを最新版にできるかどうか」**
古いPCで詰まる本当の原因は、メモリより **OS が古くてブラウザが最新版にならない** ほう。
各社がサポート対象ブラウザを公開しているので、そこが唯一の公式な線になる。判定方法をそのまま書く。

**3. 公式が出している最低要件を、出典つきで表に**
対応OS／Node.js の対応環境／Claude Code の要件。**取れたものだけ**載せる。

**4. 公式が出していないところは「出していない」と書く**
⚠️ **各社はブラウザ版AIの推奨メモリを公表していない可能性が高い。**
その場合「公式の最低メモリは存在しない」と書き、代わりに**この記事を書いた機械の実測構成**を
1行添えて、読者が自分と比べられるようにする。数字をでっち上げるより、比較対象を1つ出すほうが役に立つ。

実測して載せるのは **OS のバージョン／搭載メモリ／CPU／Node.js のバージョン** の4つ。
⚠️ **ホスト名・ユーザー名・絶対パスは載せない**（`validate.py` が `C:\Users\` を機密として弾く）。

**5. 足りないときの逃げ道**（この節で一番効くはず）

- **古いPCしかないなら、スマホのほうが速い可能性が高い。**3社ともスマホアプリがあり、
  5年前のスマホは10年前のPCより快適に動く
- ブラウザのタブを閉じる／軽いブラウザにする
- **Claude Code は諦めてブラウザ版に絞る**という選択もはっきり書く。レシピは動かせないが、AIは使える

## ⑤ 事実の取り方

公式ページを**実際に開いて生の記述を読んでから**書く。`tools/check_numbers.py` の `fetch()` が
生テキストを返すので、要約させずに自分で grep する（⚠️ 要約は、書いていないことを書くだけでなく
**書いてあることを消す**。2026-08-05 の実害を参照）。

**届かなかったページは書かない。**「公式のここに書いてあります」とリンクだけ置き、
確認できなかったと明記する（`write-or-stop` の流儀）。

⚠️ **`openai.com` は過去に bot 判定で403の実績がある**ので、ChatGPT の節が薄くなる可能性がある。
そうなったら埋めずにそのまま出す。

## ⑥ 検査

**frontmatter に `checked: YYYY-MM-DD` を足す。**出典URLの一覧は持たない
——本文のリンクから機械で拾えるので、二重に持つと必ずズレる。

⚠️ **`checked` を「この記事だけ必須」にしない。**全記事に必須にすると既存記事が全部落ちる。
かといって slug を名指しで必須にすると、2026-08-08 に撤去したばかりの `FIGURE_EXEMPT_SLUGS` と
同じ「名指しの穴」を逆向きに作ることになる。**名指しを使わずに、抜けを可視化する**形にする。

| 何 | どこ | 何をする |
|---|---|---|
| `checked` の日付が壊れている・未来日付 | `src/validate.py` | **ビルドを止める**（書いた本人がその場で直せる） |
| `checked` が無いこと自体 | — | **止めない**（既存記事が全部落ちるため） |
| 外部リンクの死活 | `tools/check_freshness.py`（新規） | 週次 |
| `checked` からの経過日数（90日） | `tools/check_freshness.py`（新規） | 週次 |
| **外部リンクを持つのに `checked` が無い記事** | `tools/check_freshness.py`（新規） | 週次で**一覧に出す**（これが「付け忘れ」の網） |
| 通知 | `.github/workflows/freshness.yml`（新規） | 問題があればワークフローを失敗させ、**GitHubの標準の失敗通知メール**で気づく |

この形なら、`/start/` に `checked` を書き忘れても週次の一覧に出るので、静かに漏れない。
既存の tools 記事3本も同じ一覧に出てくるはずだが、**それは正しい指摘**（公式の料金ページを
引用していて、実際に腐る）。今回は直さず、一覧に出させて次の判断材料にする。

⚠️ **通知コードは新設しない。**`tracker/notify.py` を呼ぶと、サイトの検査がトラッカーに依存する。
週次の検査に必要な信頼性は、GitHub の標準通知で足りる。

**確認日はページにも出す。**読者が自分で古さを判断できるほうが、こちらの検査より確実に効く。

## ⑧ テスト

- `checked` の形式検証（未来日付・読めない日付でビルドが止まる／**無いだけでは止まらない**）
- `check_freshness.py`（リンク切れ・古さ・`checked` の付け忘れ。**ネットに出ないようスタブ**）
- `/start/` がビルドされること
- 図2枚が座標検査を通ること（既存の figures 検査に自動で乗る）

## ⑨ 段取り

1. **事実の収集**（公式を実際に開く）← ここで届かないものが出たら範囲が縮む
2. 記事本体（`content/pages/start.md`）
3. 図2枚
4. トップの導線 ＋ nav
5. 検査3点（`validate.py` / `check_freshness.py` / ワークフロー）
6. テスト・ビルド・ブラウザでの厳密計測・デプロイ確認

## ⑩ やらないこと（YAGNI）

- **ツール別の4ページ**＝1枚ものを出して反応を見てから決める
- **ローカルLLM（Ollama等）の導入手順**＝運営者が使っていないので確かめられない。
  ただし「スペックの話を探している人はこれと混同している」ことだけ1段落で切り分ける
- **Mac の手順**＝確かめられないので公式へのリンクのみ
- **出典URLの frontmatter 一覧**＝本文から拾えるので持たない
- **専用の通知コード**＝GitHub の標準通知で足りる

## 想定される失敗と、そのときどうするか

| 起きうること | どうする |
|---|---|
| `openai.com` に届かない | ChatGPT の節はリンクのみにして、確認できなかったと明記 |
| ブラウザ版の最低スペックがどこにも無い | 「公表されていない」と書く。**公表されていないこと自体が答え**（普通のPCなら通る）と添える |
| 表がスカスカに見える | 空欄を推測で埋めない。「公式の記載なし」のまま出す |
